## Smaller known gaps (not blocking, not yet requested)
- **No background job runs `EpisodePruner` (Phase 30)** — `pruneAsset(assetId, {maxCount, archive})` is fully implemented and verified, but nothing calls it on a schedule; an asset with continuous execution activity accumulates episodes with no active cap beyond Redis's own 7-day TTL until something calls it.
- **Confidence calibration/tool reliability aren't wired into any live decision (Phase 30)** — `calibrateConfidence()`/`computeAgentReliability()`/`computeToolReliability()` exist and are tested against fixtures, but nothing in the planner or any agent calls them yet; there is no general-purpose tool-selection facility in the codebase to plug reliability data into (Copilot's own `selectTool()` is a stateless regex classifier, deliberately left unmodified).
- **Episode confidence is whole-execution, not per-agent (Phase 30)** — `Episode.confidence` is the run's own overall confidence (from `reflection.overallConfidence`/`consensus.confidence`/an average of step confidences); `computeAgentReliability()`'s "average confidence" per agent is therefore coarser than a true per-agent score, since per-agent confidence isn't retained on the episode itself.
- **`EpisodeStore` history is a read-modify-write JSON array, not atomic (Phase 30)** — deliberately chosen over `MemoryStore.append`/`getList` so `EpisodePruner` can remove arbitrary ids, but two concurrent `save()`s for the same asset could race and drop one id from the history list under high write concurrency; not observed in verification, but worth noting given every other store in this codebase uses the atomic `append` primitive instead.
- **No ownership check on episode ids (Phase 30)** — same "possession implies access" model every other id-shaped resource in this codebase already uses; anyone holding an `episodeId` can `GET /ai/episodes/:id` it.
- **`DebateEngine` has no HITL/resume story (Phase 29)** — a debate is one short synchronous call with no pause point; if a future write-capable, `MANUAL`-gated agent were ever added as a fifth participant, this would need designing from scratch (none of `HitlOrchestrator`/`GraphExecutor`/`LLMPlannerExecutor`'s resume mechanisms are wired to it).
- **`classifyFindings()`'s corroboration signal is single-factor (Phase 29)** — a Risk finding is "accepted" only if a Recommendation explicitly cites it; Compliance evidence for the same underlying issue with no matching Recommendation still counts as "rejected" today, which may over-report disagreement for assets where Recommendation Agent under-produces for other reasons.
- **`DebateEngine` never re-runs Discovery (Phase 29)** — it analyzes whatever Risk/Compliance/Recommendation currently compute for an asset's existing resources; a debate on an asset with stale or zero discovered resources reflects that stale/empty state, not an error but not necessarily current either.
- **`DebateMemory`/`ConsensusStore` are TTL-only with no archive or size cap (Phase 29)** — same class of gap as `PlanStore`/`ReflectionStore`/`PlannerCache`; `DebateMemory.getHistory()` reads the full per-asset id list before slicing.
- **No ownership check on `DebateEngine`'s debateId (Phase 29)** — same "possession implies access" model every other executionId-shaped id in this codebase already uses.
- **No real LLM provider is configured in this environment (Phase 28)** — `OPENAI_API_KEY` is a placeholder, so `LLMPlanner.plan()`/`revise()` always exercise the deterministic `GoalPlanner`-derived fallback path in practice; the real prompt/parse/repair/validate pipeline exists and is unit-tested (`verify-plan-validation.ts`) but has never run end to end against a real model response in this codebase.
- **`LLMPlannerExecutor` has no `resume()`/HTTP resume route of its own (Phase 28)** — a dynamic-plan execution persists a `GraphCheckpointStore` snapshot per iteration (readable via `GET /ai/langgraph/:executionId`/`:state`), but there's no `POST /ai/planner/:executionId/resume`; moot today since no agent in `PLANNER_AVAILABLE_AGENTS` is `MANUAL` by default, but would need adding if one ever were.
- **A plan naming the same agent twice only actually runs it once (Phase 28)** — `planner.executor.ts`'s `toGraphSteps()` maps every step onto its agent's one canonical LangGraph stepId (necessary so `withDependencyGate`'s `entry.stepId === dep` check keeps working for an LLM-chosen arbitrary step id); a second step for an already-used agent is silently treated as already-attempted by the idempotent replay guard rather than run again.
- **`PlannerCache`/`PlannerHistoryStore` have no size cap or archive (Phase 28)** — same TTL-only retention class of gap as `PlanStore`/`ReflectionStore`/`ApprovalStore`; `PlannerHistoryStore.list()` reads the *entire* append-only history list into memory before slicing, which will not scale past a modest number of planning calls.
- **`buildDynamicGraph()` (Phase 28) inherits `buildWorkflowGraph()`'s "six real agents only" ceiling** — an `LLMPlanStep.agent` outside `PLANNER_AVAILABLE_AGENTS` is already rejected by `validatePlan()`, so this is enforced earlier than Phase 27's own `GraphError`-at-build-time equivalent, but the underlying registry (`nodeByAgent`) is still the same one `registerGraphNode()` extends.
- **No real write-capable tool/agent to exercise MANUAL approval gating, now needed by both HITL paths (Phase 26/27)** — `HitlOrchestrator` and `GraphExecutor` each pause/resume against the same `ApprovalPolicy`/`ApprovalEngine`, but neither has a real destructive action to gate; every MANUAL/pause/resume/reject verify check for both drives a synthetic in-process fake agent.
- **`GraphExecutor.resume()` supports only one concurrently-pending `interrupt()` per execution (Phase 27)** — `Command({resume: value})`'s simple form, not the id-keyed multi-interrupt map form; fine today since at most one policy is ever `MANUAL` at a time, but a graph with two simultaneously MANUAL-gated parallel branches would need it.
- **`GraphCheckpointStore` isn't a real `BaseCheckpointSaver` (Phase 27)** — it persists plain `GraphState` JSON snapshots for `GraphExecutor`'s own resume-after-restart story, not LangGraph's internal `Checkpoint`/`channel_versions`/`versions_seen` format; can't be swapped into a different official checkpointer package without a translation layer.
- **LangGraph retry counts are metrics-only (Phase 27)** — `estateai_ai_langgraph_retries_total` is an aggregate Prometheus counter (by graphId/agentId), not a per-run field on `GraphExecutionResult` the way `AgentTaskResult.attempts` is for `WorkflowEngine`.
- **`buildWorkflowGraph()`'s agentId→node registry only covers the six real agents (Phase 27)** — a `WorkflowDefinition` referencing any other agentId throws `GraphError` at graph-build time (a caller can extend it via `registerGraphNode()`, but nothing does by default beyond the six).
- **No real write-capable tool/agent to exercise MANUAL approval gating (Phase 26)** — `ApprovalPolicy` supports `register(agentId, 'MANUAL')`, but nothing does by default (no destructive action exists yet, Phase 24's `ToolExecutor` still refuses `'write'`); every pause/resume/reject verify check drives a synthetic in-process fake agent, and there is no live HTTP path that produces a genuine `PENDING` approval request today.
- **No `(executionId, stepId)` index on `ApprovalStore` (Phase 26)** — `GET /ai/approval/pending` and any future audit query do a full scan of the pending list; `HitlOrchestrator` itself avoids needing this index by persisting the `stepId -> ApprovalRequest id` map directly in `PausedExecutionState`.
- **No durable archive for `ApprovalRequest`s (Phase 26)** — 30-day Redis TTL, same class of gap as `PlanStore`/`ReflectionStore`'s 7-day TTL; an old request silently 404s rather than being retrievable elsewhere.
- **No ownership check on `HitlOrchestrator` executionId/ApprovalRequest ids (Phase 26)** — same "possession implies access" model `GET /ai/orchestrator/status`'s `executionId` already uses; anyone holding an id can resume, approve, or reject it.
- **No LLM-driven planner or critic (Phase 25)** — `GoalPlanner`'s workflow selection and `Critic`'s scoring are both deterministic heuristics, not model calls, same limitation `Planner.resolveWorkflowId()`/`copilot.intent.ts` already had.
- **Plan Revision only removes steps, never substitutes or adds (Phase 25)** — a failed step's transitive dependents are skipped live in the same run; there is no dynamic re-planning that swaps in an alternative agent or inserts a new step.
- **The real Discovery Agent can't be used to demonstrate Plan Revision from the outside (Phase 25)** — a bad GitHub credential is caught internally and returned as a business-level `SUCCESS` output with `confidenceScore: 0`, not a thrown exception, so `verify-planning.ts`'s Plan Revision proof uses a synthetic always-throwing fake agent in-process instead.
- **`ReflectionReport` doesn't surface per-step retry `attempts` counts (Phase 25)** — only pass/fail/skip; the raw count is still on `ExecutionResult.steps[].attempts` if a caller needs it.
- **`PlanStore`/`ReflectionStore` have a 7-day Redis TTL, no durable archive (Phase 25)** — an old plan/reflection silently 404s rather than being retrievable from anywhere else.
- **No manual `POST /ai/tools/execute` HTTP route (Phase 24)** — every new tool is reachable in-process by agents/Copilot's automatic selection, never directly by an external caller; deferred given `postgres_query`'s broad, unscoped database read access.
- **No real (non-mock) web search provider, and no Copilot tool-selection trigger for it either (Phase 24)** — `MockWebSearchProvider` is the only `WebSearchProvider` implementation; `web_search` is registered and callable but nothing currently invokes it automatically.
- **`ToolRegistry.execute()` has no allowlist/permission enforcement (Phase 24)** — only calls through the new `ToolExecutor` are checked; every pre-Phase-24 agent's own internal tool calls (still using `ToolRegistry.execute()` directly) bypass the Phase 24 permission model by design, for backward compatibility. Retrofitting them to route through `ToolExecutor` (threading an `agentId`) is future work.
- **`agent-tool-access.ts`'s allowlist is a static, hand-maintained map (Phase 24)** — a new tool or agent needs a manual edit; a missed one silently denies rather than erroring at registration time.
- **The Filesystem Tool's sandbox root starts empty (Phase 24)** — `apps/api/var/fs-tool-root/` has only a `README.md`; no agent or route writes anything useful into it yet.
- **`LocalHashEmbeddingProvider` is not a real embedding model (Phase 23)** — the default (`EMBEDDING_PROVIDER=local`) captures token overlap via a deterministic hashing trick, not learned semantic meaning. `EMBEDDING_PROVIDER=openai` gives meaningfully better retrieval but requires `OPENAI_API_KEY`.
- **No embedding-provider migration/backfill tool (Phase 23)** — switching `EMBEDDING_PROVIDER` after documents already exist doesn't re-embed them; old `KnowledgeDocument` rows keep their original `embeddingVersion`/vector, silently incomparable to vectors from a newly-selected provider.
- **No reranking or hybrid search (Phase 23)** — `RetrievalService.search()` is single-pass cosine-similarity nearest-neighbor only; no keyword/BM25 hybrid, no cross-encoder reranking step.
- **`KnowledgeDocument`/`RetrievalTrace` have no cascade delete from `Asset` (Phase 23)** — same soft-reference pattern as `Finding`/`RiskScore`/`PolicyResult`; deleting an asset elsewhere in the app leaves indexed documents/traces orphaned.
- **Automatic indexing only covers the `src/ai/orchestrator/` stack (Phase 23)** — wired into exactly one hook, `executor.ts`'s `onStepComplete`; the legacy `services/agents/` orchestrator and `services/ai/`'s `ReportAgent`/`CopilotService` produce no `KnowledgeDocument` rows. A new agent added to `orchestratorAgentRegistry` also needs its own case in `ai/shared/knowledge.indexing.ts` to be indexed automatically — it isn't automatic-for-free just from registering the agent.
- **Copilot Agent intent classification is deterministic keyword regex (Phase 22)** — `copilot.intent.ts`, same limitation `Planner`'s workflow-intent classifier has. A genuinely ambiguous or creatively-phrased question falls through to the `GENERAL` catch-all rather than being understood.
- **`conversationId` has no ownership record (Phase 22)** — `GET`/`DELETE /ai/copilot/history` trust possession of the id (server-generated `randomUUID()` when the client doesn't supply one, so unguessable in practice, but not access-controlled the way an assetId-scoped route is). Same model `GET /ai/orchestrator/status`'s `executionId` already used, just not previously called out.
- **Copilot's Intelligent Routing only knows 4 fixed workflows (Phase 22)** — `copilot.executor.ts`'s `ROUTING_WORKFLOW` map (`ANALYZE`/`EXPLAIN_RISK`→`risk-only`, `EXPLAIN_COMPLIANCE`→`compliance-only`, `EXPLAIN_RECOMMENDATION`→`risk-recommendation`, `SUMMARIZE_REPORT`→`full-security-analysis`) can't compose a novel workflow for a request outside those four shapes.
- **"Explain recommendation N" indexes into a re-fetched, possibly-reordered list (Phase 22)** — if recommendations change between chat turns (e.g. a fresh discovery run), "recommendation 2" can silently refer to a different item than a few messages earlier.
- Recommendation Agent's cross-referencing (`recommendation.aggregate.ts`, Phase 21) links a risk finding and a compliance failure only when they share the exact same `resourceId` — no correlation across different resources of the same asset, and no LLM-assisted correlation of conceptually-related-but-not-identical findings.
- Report Agent's standalone memory fallback (Phase 21) covers Risk/Compliance/Recommendation (all keyed by `assetId`) but not Discovery (keyed by `accountId`) — a report generated outside a live orchestrator run always shows the Discovery section as `MISSING` unless a future phase adds an `accountId`-via-`Resource.assetId` lookup path.
- `StateManager.finalize()`'s new `context` parameter (Phase 21, fixes the previously-always-empty `agentOutputs` trace on `GET /ai/orchestrator/status`) is optional, not required — a future caller of `finalize()` that omits it silently gets the old stale-snapshot behavior back with no compiler warning.
- No manual/HTTP route to create a `Relationship` directly — all edges are discovery-derived. Would be needed if a future checkpoint wants user-declared relationships.

- No shared cross-route error-mapping helper; each route file hand-rolls its own `mapXError`. Fine at current scale, worth revisiting if route count grows significantly (see [DECISIONS.md](DECISIONS.md)).
- `Asset.riskScore`'s 0–100 bound is enforced only at the service/Zod layer, not a DB constraint.
- Rule evaluation is GitHub-only (5 rules covering `repository` resources). `user`/`organization` GitHub resources and every other provider currently produce zero findings — the same "silent no-op for unregistered provider/type" shape as relationship extraction.
- `Recommendation` copy is a static `Record<ruleCode, template>` in `recommendation.service.ts`, not a per-rule-file concern — a rule without a template entry still gets a generic fallback recommendation rather than failing, but the copy won't be specific.
- `RiskScore`'s OVERALL scope is a single global row aggregating every OPEN finding platform-wide, admin-only — there's no per-user "all my assets" rollup between ASSET scope and OVERALL scope yet.
- `Finding`/`Recommendation`/`RiskScore`/`PolicyResult` are soft-referenced (no FK) to `resourceId`/`findingId` like `Resource`/`Relationship` — see [PROJECT_PROGRESS.md](PROJECT_PROGRESS.md) for which older verify scripts leave orphaned rows as a side effect of triggering discovery.

- No manual/HTTP route to create a `Policy` or toggle `enabled` — `PolicyRepository.update()` exists and is exercised by `verify-policy.ts`, but only via direct repository calls, not an HTTP route (the Phase 6B spec's API section only listed GET routes).

- Several older verify scripts fetch asset events with the default pagination limit (20); as per-discovery event volume grows across phases this can push a script's own target events off page 1 (already hit in `verify-graph.ts`, fixed there — see [DECISIONS.md](DECISIONS.md)). `verify-resources.ts`, `verify-analysis.ts`, `verify-discovery.ts`, `verify-sync.ts`, `verify-jobs.ts` haven't hit the threshold yet but use the same unguarded pattern.

This means `DISCOVERY_SUMMARY`/`SECURITY_REPORT` reflect the asset's state as of its last completed discovery job, not a fresh live pull; there is no "run discovery then report" single request today.
- Agent `timeoutMs`/`maxAttempts` defaults (10s / 2 attempts, in `planner.service.ts`) are not currently overridable per request — a future checkpoint wanting slower agents (e.g. a real LLM call in Phase 7B) will need to extend `AgentPlanHint`/the execute request to carry per-agent overrides.

- `ReportAgent` is the only agent wired to `AIService` (Phase 7D) — `RiskAgent`/`ComplianceAgent`/`DiscoveryAgent`/`RecommendationAgent` still never call it, and no agent calls `ContextBuilder`/`KnowledgeService` directly (only `AIService` does, internally). A future phase generalizing AI integration to a 2nd agent should wait for a real 2nd consumer before extracting a shared pattern (see DECISIONS.md).

A future checkpoint wanting true "trace this one user action end-to-end" tracing would need to add and thread that field deliberately, not as a side effect of something else.
- `estateai_discovery_duration_seconds` and `job_execution_duration_seconds{type="DISCOVERY"}` (Phase 12) currently always move together in practice, since nothing calls `DiscoveryService.discover()` outside the `DISCOVERY` job type today — the distinction between "discovery's own cost" and "job-framework overhead" only becomes visibly useful if/when a non-job-queued caller of `discover()` is ever added.
- `JobService.getQueueHealth()` (Phase 12) only considers QUEUED jobs "stuck", never RETRYING ones (deliberate — a RETRYING job can legitimately wait out `JOB_RETRY_BACKOFF_MS`, up to 24h for the last configured delay) — a queue where every pending job happens to be RETRYING with a far-future `nextRetryAt` would report `queue.status: 'ok'` even if that's operationally worth a human's attention. Worth revisiting if this scenario turns out to matter in practice.
- `docker-compose.prod.yml` has no zero-downtime rolling deploy (one replica per service) — `docs/DEPLOYMENT.md`'s Scaling section describes the multi-replica-behind-nginx approach conceptually, but no ready-made multi-replica compose file ships here.
- Edge-level nginx rate limiting (Phase 12, `limit_req_zone`) and app-level `@fastify/rate-limit` are two separately-tuned limits by design (see DECISIONS.md) — no single config source drives both; a future change to one won't automatically retune the other.
- `nginx.conf`'s static-asset cache (`/_next/static/`) is the only cached route — API responses are never cached at the nginx layer (correctly, since they're per-user/JWT-authenticated), so there's no cache-invalidation concern to track, but also no caching benefit for any API traffic even where a response might theoretically be cacheable (e.g. `GET /policies`, organizational catalog data reachable by any authenticated user).
- `docs/DEPLOYMENT.md`'s backup/restore guide covers Postgres only (`pg_dump`/`psql`) — no automated backup scheduling ships with this repo; "run this on a schedule" is left to the deployer's own infra (cron, a platform's scheduled-job feature, etc.).
- **No real cross-asset dashboards (Phase 13)** — `/discovery`, `/findings`, `/recommendations`, `/compliance`, `/reports`, `/accounts`, `/resources`, `/activity` are asset-scoped landing pages (pick an asset, then see that asset's data), not aggregate cross-asset views, because no bulk endpoint exists for any of these domains. A real fix needs new backend endpoints (e.g. "findings across all my assets"), out of Phase 13's frontend-only scope — see DECISIONS.md.
- **No real AI Copilot streaming (Phase 13)** — `useTypewriter` is a client-side reveal animation over an already-complete response. `CopilotService` (Phase 8) never calls `provider.stream()`; every AI provider already implements `stream()` (Phase 7B) but nothing calls it anywhere in the codebase. A real streaming endpoint (`POST /copilot/chat/stream`, SSE) would be a backend change.
- **No server-side Copilot conversation memory (Phase 13, echoes Phase 8)** — conversation history is `localStorage`-only, per browser, per asset. Doesn't sync across devices/browsers, is lost if the user clears site data, and is never sent to the API as prior turns.
- **No Compliance Trend / Discovery Trend charts (spec'd at Phase 13, not built)** — no persisted compliance snapshot history and no discovery-duration time-series list endpoint exist on the backend. Building these charts for real needs a backend feature first (e.g. periodic compliance snapshots, or a `GET /discovery-runs` style endpoint) — fabricating chart data client-side was considered and rejected as actively misleading for a security product.
- **No true global search index (Phase 13)** — `/search` composes `GET /assets?search`, `GET /policies?search` (both global) with resources/findings scoped to the last-picked asset only. A real global search across every domain (especially resources/findings across every asset, not just one) would need either a dedicated backend search endpoint or client-side aggregation across every asset (expensive — same N+1 concern as the dashboard sampling).
- `apps/web` still has two coexisting data-fetching patterns — Phase 9's `useApiQuery` (Dashboard, Assets, and the five un-migrated Phase 9 view files) and Phase 13's TanStack Query (every other new page). Deliberate for now (see DECISIONS.md) but worth finishing the migration in a future frontend-focused phase so it doesn't become permanent.
- `FindingsView`/`RiskView`/`ComplianceView`/`DiscoveryView`/`NewAssetForm` (Phase 9, all under `app/assets/[id]/`) still use the original hardcoded `slate-*` Tailwind classes, not Phase 13's CSS-variable theme tokens — functionally correct but visually inconsistent in dark mode.
- `apps/web` still has no automated test suite (Playwright/Vitest) — see the "Explicitly deferred" section above; Phase 13 verified via `pnpm lint`/`pnpm build` plus manual dev-server smoke testing, same as Phase 9's own verification approach.
- Several forms (`NewAssetForm`, `ConnectAccountForm` inside `AccountsView`) were not migrated to React Hook Form + Zod — only the login form was, given this phase's overall size. They still work (hand-rolled `useState` per field), just don't share the new form-validation pattern.
- Dashboard's per-asset aggregate sampling (10 most-recently-updated assets for Connected Accounts/Open Findings/Compliance Score/Recent Events) will undercount for any user with more than 10 assets — see DECISIONS.md. A real fix needs backend bulk-aggregate endpoints, not a larger client-side sample size (which would just make the dashboard slower).
- **No TLS termination in `nginx.conf` (still true as of Phase 14)** — `docs/DEPLOYMENT.md`'s "TLS" section now documents the two real options (front it with a cloud LB/Cloudflare, or add a `listen 443 ssl` block with real certs) but neither is configured out of the box; certs are deployment-specific.
- **OpenTelemetry is documented, not implemented (Phase 14)** — `docs/DEPLOYMENT.md`'s Monitoring guide explains what adding it would take (`@opentelemetry/sdk-node` + Fastify/`pg`/`ioredis` auto-instrumentation + an OTLP exporter) but none of it exists in `apps/api` today. The natural next step if end-to-end HTTP→job→AI tracing (see the correlation-id gap above) is ever prioritized.
- **No Grafana dashboard or Alertmanager config ships (Phase 14)** — `docs/DEPLOYMENT.md` documents which `/metrics` series to build panels from and gives starting-point alert thresholds, but there's no dashboard JSON or alerting-pipeline config in this repo; both are deployment-specific to wire up for real.
- **`docker-compose.prod.yml` doesn't set Docker log-driver rotation (Phase 14)** — `docs/DEPLOYMENT.md`'s Log rotation guidance covers the fix (`max-size`/`max-file` on the `json-file` driver, or a log-shipping agent instead), but the compose file itself doesn't set it yet; unbounded log growth on a long-running host until it is.
- **`GET /health/ready` returns an unhandled 500, not a graceful 503, when the database schema doesn't exist yet (found during Phase 14's smoke test)** — the route assumes a reachable database implies a queryable one; a reachable-but-pre-migration database throws instead. Low priority (the fix is "run migrations," which happens anyway) but a legitimate small bug for whichever future phase next touches `src/routes/health.ts`. Not fixed in Phase 14 per its "do not change business logic" scope.
- **`pnpm prisma:seed` now requires a prior `pnpm build` (Phase 14)** — the seed script moved from a standalone `tsx`-executed file to a normally-compiled `src/scripts/seed.ts` (see DECISIONS.md for why: the production image ships `dist/` only). Same prerequisite `pnpm start` already has; not a new class of friction, but worth remembering if it trips up a fresh local setup.
