# Project Progress

EstateAI is a multi-agent digital asset/continuity SaaS backend. Development proceeds in mentor/pair-programming style, one checkpoint at a time: each checkpoint is fully implemented, verified (format/lint/build + verification scripts + full regression), and explained, then work stops for explicit user review before the next checkpoint begins.

## Status: Phase 30 complete, awaiting review for the next checkpoint

## Completed phases

### Phase 1–2 — Foundation & Auth
Fastify + TypeScript scaffold, PostgreSQL via Prisma, Redis. User registration/login, JWT access tokens + rotating refresh tokens (with reuse-detection revoking all of a user's tokens), password hashing (bcrypt), `GET /auth/me`.

### Phase 3 — Asset domain
`Asset`, `AssetCategory`, `Tag`/`AssetTag`, `AssetEvent` (append-only timeline) — full CRUD, ownership enforcement (`getOwnedAsset`), search/filter/pagination on assets, tag attach/detach, event creation and listing. `Account` model + connect/list/update/disconnect (credentials encrypted at rest, AES-256-GCM). ### Phase 4 — Asynchronous Execution Platform (complete)

Verification: `verify:jobs` (33 checks) + full regression suite. Two real bugs found and fixed (see [CHANGELOG.md](CHANGELOG.md)).

### Phase 7A — Multi-Agent Intelligence Platform (orchestration only, no LLMs) (complete)
Deterministic agent orchestration platform sitting on top of every prior phase — never a new source of business logic, only a coordination layer over existing services. Registry pattern (`Agent` interface: `id()`/`supports()`/`plan()`/`execute()`, no switch statements) with 5 agents: `DiscoveryAgent` (resource/graph summary via `ResourceSearchService`+`GraphService` — deliberately does not call `DiscoveryService.discover()`, see DECISIONS.md), `RiskAgent` (`FindingService`+`RiskService`), `ComplianceAgent` (`ComplianceService`), `RecommendationAgent` (`RecommendationService`), `ReportAgent` (pure aggregation of the other four, no service of its own). `PlannerService.createPlan()` turns a request type + `AgentContext` into an `ExecutionPlan` by asking the registry which agents `supports()` that request type, then asking each agent's `plan()` for its dependencies — the planner itself knows only request types, never providers or which concrete agents exist. `TaskService` partitions the resulting dependency graph into waves (Kahn's-algorithm-style: same-wave tasks run in parallel via `Promise.all`, later waves run sequentially), with per-task retry (`maxAttempts`), timeout (`Promise.race`), and pre-emptive skip on `AbortSignal`/upstream-failure. `AgentOrchestrator.execute()` runs the full Planner → Task Graph → (registry-resolved) Agents → Result Aggregator pipeline synchronously in-request (not job-queued — every agent only reads already-persisted data). `AgentContext` is the "shared context": a per-run cache (`getOrLoad`) so two agents needing the same read only issue it once, plus a `results` map so downstream agents (`ReportAgent`) read upstream agents' outputs directly. `ResultAggregatorService` merges per-agent outputs keyed by `agentId` while preserving per-task provenance (status/timing/attempts) separately. New `AgentPlanExecution` model (migration `20260721183220_add_agent_platform`) — one audit row per plan run, written at start (RUNNING) and completion (COMPLETED/FAILED + summary JSON), purely to back `GET /agents/plans/:id`; not a queue, not retried. Request types: `DISCOVERY_SUMMARY`, `RISK_SUMMARY`, `COMPLIANCE_SUMMARY`, `RECOMMENDATIONS` (single-agent), `SECURITY_REPORT` (full 5-agent pipeline: discovery/risk/compliance run in parallel, recommendation depends on risk, report depends on all four). Events: `PLAN_CREATED`/`AGENT_STARTED`/`AGENT_COMPLETED`/`AGENT_FAILED`/`PLAN_COMPLETED`. New `POST /agents/execute`, `GET /agents`, `GET /agents/plans/:id` route family.
Verification: `verify:agents` (60 checks — includes direct in-process unit checks for task-graph wave partitioning, cycle detection, retries, timeouts, cancellation, shared-context caching, and registry/planner extensibility, alongside full HTTP integration checks) + full regression (24 verification scripts, all green).
Explicitly excluded (per spec): OpenAI/Claude/Gemini/any LLM, LangChain/LangGraph, vector databases, embeddings, semantic search — this phase is orchestration only, deferred to Phase 7B.

### Phase 7B — AI Integration Framework (provider abstraction only, no memory/RAG) (complete)
A vendor-neutral LLM abstraction layer sitting beside (not inside) Phase 7A's agent platform — `services/ai/` is a new peer domain, not a modification to any existing agent. Registry pattern (`AIProvider` interface: `id()`/`supports(model)`/`models()`/`generate()`/`stream()`/`estimateCost()`/`countTokens()`) with 3 self-contained provider adapters — `ClaudeProvider` (`claude-opus-4-8`/`claude-sonnet-5`/`claude-haiku-4-5-20251001`), `OpenAIProvider` (`gpt-4o`/`gpt-4o-mini`/`gpt-4.1`), `GeminiProvider` (`gemini-2.0-flash`/`gemini-1.5-pro`) — each translating a shared, provider-independent `AIRequest`/`AIResponse` shape into its own vendor wire format, same convention as the three separate GitHub oauth/sync/discovery providers (no vendor JSON leaks outside its own file). `PromptBuilder.build()` produces the provider-independent "Final Prompt" (system prompt + rendered context blocks + user prompt) with zero knowledge of providers *or* of `services/agents` — it takes plain strings/objects, not an `AgentContext`/`AgentResult`, so it's equally usable by today's standalone `POST /ai/generate` and by a future agent integration. `AIService.generate()` is the single chokepoint every AI call flows through: resolves a provider (explicit `provider`, else by `model` via `aiProviderRegistry.resolveForModel()`, else `AI_PROVIDER` config default), builds the prompt, retries only *transient* provider errors (5xx/timeout) up to `AI_MAX_RETRIES` with a fixed backoff (a permanent rejection — bad key, malformed request — fails immediately, same permanent-vs-retryable distinction jobs draw), persists one `AIRequestLog` audit row per call (write-once, unlike `AgentPlanExecution`'s start/complete pair), and emits events. Shared, non-duplicated utilities: `token-counter.ts` (a documented chars/4 approximation, not a real per-vendor tokenizer) and `cost-estimator.ts` (a static, illustrative per-model USD/1M-token pricing table with a default fallback for unrecognized models). `response-parser.ts` is the shared "attach cost + latency" step every provider's `generate()` calls after parsing its own vendor JSON. New `AIRequestLog` model (migration `20260722181713_add_ai_integration_framework`). New `AI_PROVIDER`/`CLAUDE_API_KEY`/`OPENAI_API_KEY`/`GEMINI_API_KEY`/`CLAUDE_API_URL`/`OPENAI_API_URL`/`GEMINI_API_URL`/`AI_DEFAULT_MAX_TOKENS`/`AI_MAX_RETRIES`/`AI_RETRY_BACKOFF_MS`/`AI_REQUEST_TIMEOUT_MS` config, the URL vars overridable exactly like `GITHUB_*_URL` so `verify-ai.ts` can point at local mock provider servers instead of live vendor endpoints. Events: `AI_REQUEST_STARTED`/`AI_REQUEST_COMPLETED`/`AI_REQUEST_FAILED`/`TOKEN_USAGE_RECORDED`. New `POST /ai/generate`, `GET /ai/providers`, `GET /ai/models` route family.
Verification: `verify:ai` (46 checks — provider registry/selection, prompt building, token counting, cost estimation, response parsing, all 3 providers' `stream()` against their own mock, retries, permanent-failure short-circuit, usage-log persistence, ownership/auth, events) + full regression (26 verification scripts, all green).
Explicitly excluded (per spec): memory, RAG, vector database, embeddings, semantic search, autonomous agent loops — and, per this session's own scoping decision, no existing agent was wired to actually call `AIService` yet (see DECISIONS.md); that integration is deferred to a later checkpoint.

### Phase 7C — Knowledge Retrieval & Context Builder (complete)
A reusable retrieval layer sitting between Phase 7A's agents and Phase 7B's `AIService`/`PromptBuilder`, so future agents (and today's `AIService`) never have to manually gather context before calling AI. Registry pattern (`Retriever` interface: `id()`/`supports(request)`/`retrieve(request)`) with 6 retrievers, each a thin adapter that only calls an existing service (never Prisma directly): `ResourceRetriever` (`ResourceSearchService`, relevance = recency decay), `GraphRetriever` (`ResourceSearchService`+`GraphService`, bounded 10-resource sample same convention as `DiscoveryAgent`), `FindingRetriever` (`FindingService`, relevance reuses `config.risk.weights` — the same `RISK_WEIGHT_*` config `RiskService` scores with, not a second hardcoded scale), `PolicyRetriever` (`ComplianceService`, fixed relevance for failures since `PolicyOutcome` doesn't carry severity), `RecommendationRetriever` (`RecommendationService`, relevance also reuses `config.risk.weights` since `Recommendation.priority` is itself a `FindingSeverity`), `RiskRetriever` (`RiskService`, fixed top relevance). `KnowledgeService.retrieveAndBuildContext()` resolves every retriever that `supports()` the request, runs them in parallel (no inter-retriever dependencies, unlike Phase 7A's agent task graph), then merges: exact-duplicate removal by `entityKey`, "summarize repeated entities" collapsing by `groupKey` once a group exceeds `KNOWLEDGE_COLLAPSE_THRESHOLD` (keeps the highest-relevance members, folds the rest into one synthetic summary item), sort-by-relevance, and trims lowest-relevance items first (across the whole context, not per-section) until the estimated token cost (reusing Phase 7B's `token-counter.ts`) fits `KNOWLEDGE_MAX_CONTEXT_TOKENS`. `ContextBuilder.build()` is the thin front door: ownership check, brackets the call with `CONTEXT_BUILD_STARTED`/`CONTEXT_BUILD_COMPLETED` events (mirroring `AgentOrchestrator`'s `PLAN_CREATED`/`PLAN_COMPLETED`), delegates the real work to `KnowledgeService` (which itself emits one `RETRIEVAL_COMPLETED` event per retriever). **`PromptBuilder` was modified** to consume a strongly-typed `KnowledgeContext` instead of Phase 7B's freeform `contextBlocks` record — a type-only dependency on the knowledge domain's DTO, not a call into it, so `PromptBuilder` stays a pure function of its inputs. **`AIService.generate()` was modified** (per this session's scoping decision, confirmed with the user) to auto-build a `KnowledgeContext` via `ContextBuilder` whenever `assetId` is provided, before calling `PromptBuilder` — every asset-scoped `POST /ai/generate` call is now automatically grounded in that asset's current resources/findings/policies/recommendations/risk, with no Phase 7A `Agent` class touched. Context-building failures degrade gracefully (best-effort, `generate()` proceeds without context rather than failing the whole call). No new Prisma model this phase — a stateless read pipeline, same as `POST /ai/generate` itself. New `KNOWLEDGE_MAX_CONTEXT_TOKENS`/`KNOWLEDGE_COLLAPSE_THRESHOLD` config. New `POST /knowledge/context`, `GET /knowledge/retrievers` route family.
Verification: `verify:knowledge` (33 checks — registry, in-process unit checks for dedupe/collapse/trim against fake focus-gated retrievers, full-pipeline integration against real discovery-populated data, `GET /knowledge/retrievers`, `PromptBuilder` rendering a real `KnowledgeContext`, confirming the actual wire request `AIService` sends to a mock Claude server carries the rendered context sections, ownership/auth, events) + full regression (27 verification scripts, all green, including an update to `verify-ai.ts`'s now-outdated `contextBlocks` unit test).
Explicitly excluded (per spec): memory, vector database, embeddings, RAG, agent integration (no Phase 7A `Agent` class was modified — only `AIService`/`PromptBuilder`, both Phase 7B's own files), autonomous loops.

### Phase 7D — AI Report Agent (complete)
Proves the full Phase 7A → 7B → 7C architecture end to end by integrating AI into exactly one production agent — `ReportAgent` — while leaving `RiskAgent`/`ComplianceAgent`/`DiscoveryAgent`/`RecommendationAgent` untouched, per spec. `POST /agents/execute` gained an optional `aiMode` (`OFF` default / `SUMMARY` / `FULL_REPORT`), threaded through `AgentContext` (a new 4th constructor field, defaulted so every pre-existing call site keeps working unchanged) — only `ReportAgent` reads it. When `aiMode` is `OFF` (or omitted), `SECURITY_REPORT`'s response is byte-for-byte the Phase 7A structured report; when `SUMMARY`/`FULL_REPORT`, `ReportAgent` additionally calls `aiService.generate()` — the exact same chokepoint `POST /ai/generate` uses, which (per Phase 7C) auto-grounds itself in the asset's real data via `ContextBuilder` whenever `assetId` is set, so `ReportAgent` never had to call `ContextBuilder`/`KnowledgeService` itself. Three new prompt templates live outside both `ReportAgent` and `PromptBuilder` (`services/ai/prompts/`): `executive-summary.prompt.ts` (`SUMMARY` mode), `risk-summary.prompt.ts` (a composable fragment, not used standalone yet), and `security-report.prompt.ts` (`FULL_REPORT` — composes the other two plus three more sections, fixing five Markdown headings in order). `ReportAgent`'s response parser splits the AI response's raw text back into `AIReport` fields by those fixed headings — a best-effort text convention, not a schema contract. AI failure of any kind (permanent error, exhausted retries, timeout) is caught in one place and turned into `{aiStatus: 'FAILED', error}`, never thrown — the structured report is computed first and is never affected, so `SECURITY_REPORT` degrades to exactly its Phase 7A shape (plus one marker) under a total AI outage. `ReportAgent.plan()` widens its task timeout to 30s only when `aiMode !== OFF`, since an AI round trip doesn't fit the 10s default sized for read-only aggregation. New events: `AI_REPORT_STARTED`/`AI_REPORT_COMPLETED`/`AI_REPORT_FAILED`. No new route (additive to the existing `POST /agents/execute`) and no new migration (the AI narrative is computed per-request, never persisted).
Verification: `verify:ai-report` (24 checks — AI disabled/summary/full-report modes, prompt selection against the real wire request, provider selection, graceful failure via a togglable mock-server failure switch, AI metadata shape, event generation, authorization) + full regression (28 verification scripts, all green).
Explicitly excluded (per spec): memory, RAG, embeddings, vector database, MCP, LangChain/LangGraph, multi-agent collaboration, autonomous loops — and, per the spec's own scope, AI integration for any agent other than `ReportAgent`.

### Phase 8 — AI Security Copilot (complete)
The second consumer of `AIService`'s auto-grounding chain, alongside `ReportAgent` (Phase 7D) — `CopilotService` proves the chain generalizes to a genuinely different shape (a free-form question, not a fixed report template) with zero changes to `AIService`/`ContextBuilder`/`KnowledgeService`/`PromptBuilder`. `POST /copilot/chat` takes `{assetId, message}`, checks ownership explicitly, calls `aiService.generate({assetId, systemPrompt: <copilot persona>, prompt: message, focus})` — the same call `ReportAgent`/`POST /ai/generate` make — and passes the response straight through: `answer` is `response.text` verbatim, `citations` is `response.citations` verbatim (currently always absent, since `ClaudeProvider` never populates that field). This is the thinnest AI-consuming service in the codebase — no retrieval logic (spec's explicit "Do NOT duplicate retrieval logic"), no response parsing (unlike `ReportAgent`'s heading-based `parseNarrative()`), since there's no sub-structure in a single conversational answer to extract. AI failure is caught in one place and turned into `{status: 'FAILED', error}`, never thrown — the request still returns 200. New events: `COPILOT_CHAT_STARTED`/`COPILOT_CHAT_COMPLETED`/`COPILOT_CHAT_FAILED`. New `POST /copilot/chat` route. No new migration (fully stateless — no conversation/session model of any kind).
Verification: `verify:copilot` (16 checks — success with grounded answer/citations-shape/AI metadata, grounded responses verified against the real wire request's rendered `KnowledgeContext` sections, authorization, AI failure via a togglable mock-server switch, event generation) + full regression (29 verification scripts, all green).
Explicitly excluded (per spec): memory, RAG, embeddings, vector database, streaming, multi-agent workflows.

### Phase 10 — Real-Time Platform (complete)
Adds a `GET /ws` WebSocket endpoint broadcasting live `AssetEvent`s, without modifying a single existing REST route or business service beyond one hook. The insight that made this a small, low-risk change: every event type the system has ever emitted (job, discovery, agent, AI report, copilot, asset events) already flows through one function, `EventService.createForAsset()` — so that's the only business-service file touched (one `try { realtimeBus.publishAssetEvent(...) } catch {}` call after the existing DB write). `services/realtime/realtime-bus.ts` is a generic, protocol-agnostic in-process `EventEmitter`-based pub/sub with no WebSocket knowledge; `services/websocket/` (`connection-registry.ts`, `websocket-auth.ts`, `websocket-gateway.ts`, `dto/messages.ts`) is the only subscriber and the only place `ws`/`@fastify/websocket` is ever imported. Auth travels as `?token=...` (a browser WebSocket can't set an `Authorization` header), verified once at connect via the same `verifyJwtService`+`userRepository` pieces REST auth already uses; a `subscribe` message is authorization-checked via the same `getOwnedAsset()` every other asset-scoped endpoint uses. No session state persists across connections — a reconnecting client must resend `subscribe` for everything it still cares about (deliberate, not a gap — see DECISIONS.md). On the frontend, `RealtimeProvider` owns one reconnecting-with-backoff WebSocket connection per session, and `useAssetEvents`/`useMultiAssetEvents` are the two hooks every page uses to listen; live behavior was wired into Dashboard (auto-refresh), Discovery/Overview (live job status), Risk/Compliance/Findings (live refresh), Report (live agent-progress log), and every asset-scoped page (toast notifications) — all without a single new route.
Verification: `verify:websocket` (15 checks — authentication including a `4401` close on bad/missing token, subscribe/unsubscribe including malformed-message resilience, authorization isolation between users, event delivery for both a direct `AssetEvent` and a real multi-agent `SECURITY_REPORT` run's live `PLAN_*`/`AGENT_*` events, disconnect/reconnect) + full regression (30 verification scripts, all green). `pnpm format`/`lint`/`build` clean on `apps/api`; `pnpm lint`/`pnpm build` clean on `apps/web` (two new React-Compiler-era `eslint-plugin-react-hooks` rules — `react-hooks/refs`, `react-hooks/immutability` — required moving two ref-mutations from render bodies into their own effects; a real, if minor, correctness fix, not just lint-appeasement).
Explicitly excluded (per spec): streaming AI tokens, conversation memory, RAG, vector database.

### Phase 21 — Multi-Agent Collaboration & Shared Context (complete)

**Recommendation Agent** never generates a recommendation itself — it wraps the already-existing `RecommendationService`/`RecommendationRepository` (which has generated one `Recommendation` row per `Finding` since Phase 6A, as a side effect of `FindingService.evaluateResources()`), then merges those rows with the Risk Agent's findings and the Compliance Agent's policy failures. Its core new module, `recommendation.aggregate.ts`, reads a sibling step's live output straight off `OrchestrationContext.agentOutputs` (populated by `Executor` between DAG waves) when available; when Risk Agent didn't run in the same workflow (or ran but failed), it falls back to a direct `FindingService` read via its own tool so it still works standalone; Compliance has no equivalent standalone fallback, so a missing/failed Compliance step just means no compliance cross-references, never a failed run. **Shared state additions.** `AgentOutputEntry` (`ai/orchestrator/execution.context.ts`) gained two additive, optional fields — `durationMs` and `confidence` — populated by `Executor.run()`'s `onStepComplete` callback (`durationMs` from the step's own `AgentTaskResult`; `confidence` read opportunistically off `output.confidenceScore`, which every agent from Discovery onward exposes). ### Phase 23 — Long-Term Memory & Retrieval-Augmented Generation (RAG) (complete)
Adds a persistent Knowledge Base + vector search on top of the six agents Phase 16-22 built, without replacing any existing workflow or route. Three new independent layers under `apps/api/src/ai/`:

- **`ai/embeddings/`** — provider-abstracted embedding service (`EmbeddingProvider` interface mirroring `LLMProvider`'s shape), selected once at composition-root time from `EMBEDDING_PROVIDER` (`local` default, `openai` opt-in). `LocalHashEmbeddingProvider` is a dependency-free, deterministic hashing-trick embedder (SHA-256 token buckets into a fixed 1536-dim vector, L2-normalized) — chosen as the default so indexing/retrieval/Copilot grounding all work in dev/CI with zero external API key, the same "graceful default over a hard external dependency" precedent every agent's LLM-narration fallback already established. `OpenAIEmbeddingProvider` calls the real `/v1/embeddings` endpoint when opted in. Every provider's output is padded/truncated to the same fixed `EMBEDDING_DIMENSION` (1536) so the vector column stays meaningful across a future provider swap; `embeddingVersion` records which provider/model actually produced a given vector.
- **`ai/knowledge/`** — the Knowledge Store. `KnowledgeDocument` (new Prisma model, `assetId`/`agent`/`documentType`/`text`/`metadata`/`tags`/`embeddingVersion`/`embedding vector(1536)`) is the storage unit; `embedding` is declared via Prisma's `Unsupported("vector(1536)")` type (Prisma has no native pgvector support) and read/written entirely through `$queryRaw`/`$executeRaw` in `knowledge.repository.ts` — the generated client has no field for it at all. `KnowledgeStore.indexDocument(s)` embeds text then upserts by `(sourceId, agent)`: a document representing a **live entity** (a Finding, a Recommendation, an open compliance failure) updates in place on re-index; a document representing a **run-level snapshot** (a Risk/Compliance/Report/Discovery overview) gets a fresh `sourceId` per run (keyed by that run's `metadata.finishedAt`) so history *accumulates* rather than being overwritten — the deliberate design choice that makes "what changed since last scan?" answerable at all.
- **`ai/retrieval/`** — `RetrievalService.search()`: embeds a question, runs a pgvector cosine-similarity nearest-neighbor query (`<=>` operator, `1 - distance` as score so higher-is-better matches every other score in this codebase) scoped by `assetId`/`documentType`/`agent`/`tags`, and writes a `RetrievalTrace` row (document ids, scores, latency, embedding version) for every query — write-once, best-effort (a trace-persistence failure never fails the caller's actual search result, same "observability must not affect correctness" precedent `ExecutionHistory` already set).

**Automatic Indexing** (no manual trigger) is wired into exactly one place — `orchestrator/executor.ts`'s existing `onStepComplete` callback — via a new `ai/shared/knowledge.indexing.ts`/`knowledge.adapters.ts` pair (same "shared adapter, not agent-to-agent coupling" pattern `finding.adapters.ts` established in Phase 21): every successful Discovery/Risk/Compliance/Recommendation/Report step, from *any* workflow, is embedded and persisted with zero per-workflow code to remember to add. It's fire-and-forget (`void indexAgentOutput(...)`) and swallows its own errors — indexing must never affect the workflow it's observing, mirroring Phase 21's Failure Isolation precedent.

**Copilot Integration**: `copilot.executor.ts` gained a `retrieveGrounding()` step — right before generating an answer, it searches the Knowledge Store scoped to the already-ownership-verified `assetId` (never unscoped, which would let one user's question surface another user's indexed findings) and folds retrieved document text into the deterministic `CopilotExplanation.evidence`, which `copilot.prompts.ts`'s "grounded only in the above" LLM prompt already treats as ground truth — so RAG grounding required no prompt change, only new evidence flowing into an existing "never invent a fact" contract. Retrieved document ids surface on the response as `citations`.

**APIs**: `POST /knowledge/index`, `POST /knowledge/search`, `GET /knowledge/document/:id`, `GET /knowledge/history/:assetId` (`apps/api/src/routes/knowledge-rag.ts`) — ownership-checked via `getOwnedAsset()` exactly like every asset-scoped route, and deliberately in a new file/route-set distinct from the pre-existing, unrelated `routes/knowledge.ts` (Phase 7C `KnowledgeService`/`ContextBuilder`, `/knowledge/context` + `/knowledge/retrievers` — untouched).

**Infrastructure**: the local/dev/prod Postgres image (`docker-compose*.yml`) switched from `postgres:16` to `pgvector/pgvector:pg16` — a drop-in image built on `postgres:16` that adds the `vector` extension; the Phase 23 migration (`20260803063416_add_knowledge_rag`) runs `CREATE EXTENSION IF NOT EXISTS vector` plus an `ivfflat` cosine-distance index on `KnowledgeDocument.embedding`.

Verification: `pnpm build`/`pnpm lint` clean; new `verify:rag` (20 checks — automatic indexing after a real orchestrator run, manual index/search, `RetrievalTrace` persistence, Copilot grounding/citations, ownership), `verify:vector-search` (15 checks — embedding determinism, cosine ranking, topK, documentType/tag filters, cross-asset isolation, upsert-by-sourceId), `verify:memory` (12 checks — history accumulation across multiple runs vs. in-place updates for live entities, Copilot conversation memory carrying citations across follow-up turns, backward compatibility with the legacy `/copilot/chat` and `GET /ai/orchestrator/workflows`) all pass against a live dev server. Full regression sweep (`verify:ai-foundation` through `verify:copilot-agent`, plus the legacy `verify:copilot`/`verify:agents`/`verify:discovery`/`verify:knowledge`/`verify:jobs`) re-run and passes unchanged.

Explicitly out of scope / deferred (per spec, and consistent with prior phases' "illustrative, not certified" precedents): a real per-vendor tokenizer/embedding-cost tracker; a reranking step after the initial vector search; hybrid (keyword + vector) search; embedding backfill/migration tooling for switching `EMBEDDING_PROVIDER` after documents already exist (old vectors keep their original `embeddingVersion` and are simply incomparable to new ones until re-indexed); and any further AI agent phase.

### Phase 24 — Tool-Using Agents (MCP-style Tool Framework) (complete)
Upgrades EstateAI from a knowledge-aware multi-agent platform into a tool-using one: a generic, reusable Tool framework in `apps/api/src/ai/tools/` (extending, not replacing, the Phase 16 `ToolRegistry`), five new agent-agnostic builtin tools (Postgres/GitHub/Filesystem/Web Search/Knowledge Search), a permission model, a persisted execution trace, and Copilot automatic tool selection.

**The framework extends `ToolDefinition` additively** — `id?` and `permissions?: ToolPermission[]` (`'read'|'write'|'network'|'database'|'filesystem'`), both optional and defaulted (`id` → `name`, `permissions` → `['read']`) inside `ToolRegistry.register()`, so every tool registered before this phase (Discovery/Risk/Compliance/Recommendation/Report/Copilot's own tools) keeps working with zero per-file edits. New `ai/tools/` modules: `tool-context.ts` (`ToolContext` = an alias for `AIContext`, not a new type), `tool-result.ts` (`ToolResult` — the non-throwing envelope), `tool-error.ts` (`ToolError` = an alias for the existing `ToolExecutionError`), `tool-permissions.ts` (`assertPermitted()` — refuses any tool declaring `'write'`, the only permission not granted in this deployment), `agent-tool-access.ts` (a per-agent allowlist: `AGENT_TOOL_ACCESS`/`isToolAllowedForAgent()`), and `tool-executor.ts` (`ToolExecutor` — the new entry point wrapping `ToolRegistry` with allowlist + permission enforcement, telemetry, and a persisted `ToolExecutionTrace` row; never throws, always resolves a `ToolResult`).

**Five new builtin tools** (`ai/tools/builtin/`), each agent-agnostic (shared by whichever agents are declared for them in `agent-tool-access.ts`, not owned by one agent's folder):
- **Postgres Tool** (`postgres_query`/`postgres_list_tables`/`postgres_table_info`) — read-only. `postgres_query` rejects anything not a single `SELECT`/`WITH ... SELECT` statement (write/DDL keywords, multiple statements) before it ever reaches Postgres; `postgres_table_info` only interpolates a table name after confirming it via `information_schema` first, closing the identifier-injection gap a naive query would have.
- **GitHub Tool** (`github_repository_info`/`github_repo_branches`/`github_list_files`/`github_commit_history`/`github_list_pull_requests`/`github_list_issues`) — live, read-only GitHub REST calls (self-contained, same pattern `GitHubDiscoveryProvider`/`GitHubSyncProvider` already use), ownership-checked via the existing `getOwnedAccount()`. Distinct from, and does not modify, Discovery Agent's own `github.tool.ts` (which wraps `DiscoveryService`/persisted `Resource` rows, not live API calls) — `github_repo_branches` is named to avoid colliding with Discovery's pre-existing placeholder tool of the (almost) same name.
- **Filesystem Tool** (`fs_read_file`/`fs_list_directory`/`fs_search_files`) — read-only, sandboxed to `apps/api/var/fs-tool-root/`; every path is resolved and verified to stay inside that root before any `fs` call runs. No write operation exists on this tool's surface at all.
- **Web Search Tool** (`web_search`) — an interface (`WebSearchProvider`) plus one mock implementation (`MockWebSearchProvider`, deterministic, no network, `example.com` placeholder results) — a real provider plugs in later behind the same interface, mirroring `EmbeddingProvider`'s (Phase 23) swappable-provider shape.
- **Knowledge Search Tool** (`knowledge_search`) — wraps `RetrievalService.search()` (Phase 23) as a Tool. `copilot.executor.ts`'s RAG grounding now calls this tool via `ToolRegistry`/`ToolExecutor` instead of importing `RetrievalService` directly, per the spec's "agents should use it through the Tool framework instead of directly."

**Every agent declares which tools it can use** — `agent-tool-access.ts`'s `AGENT_TOOL_ACCESS` map lists each of the six agents' own tools plus whichever generic builtin tools it plausibly needs (e.g. Compliance gets the Postgres tools, Copilot gets all five builtin families). `ToolExecutor.run()` enforces this allowlist before every call; `ToolRegistry.execute()` itself stays allowlist-agnostic, so every pre-Phase-24 internal call site (each agent's own executor calling its own tools directly) is unaffected.

**Copilot automatic tool selection** (spec #8) — a new `copilot.tool-selector.ts` (`selectTool()`), deterministic keyword matching in the same "not an LLM call" spirit as `copilot.intent.ts`/`Planner`, maps a chat message to a tool call: "list open GitHub issues" → `github_list_issues`, "search previous findings" → `knowledge_search`, "count findings" → `postgres_query` (a **fixed, code-authored** count query scoped to the resolved `assetId` — never the caller's raw message text, since `postgres_query` grants broad read access to the whole database with no per-row authorization of its own). A match short-circuits `copilot.executor.ts`'s normal intent-based explanation flow entirely, runs the selected tool through `ToolExecutor` (so allowlist/permission/trace all apply), and renders the result as the answer's evidence via a new generic `summarizeToolOutput()` helper. A message that matches nothing falls through to the unchanged Phase 22 intent-based flow.

**Tool Execution Trace** (spec #9) — a new `ToolExecutionTrace` Prisma model (`toolName`/`agentId`/`arguments`/`success`/`error`/`durationMs`), written by `ToolExecutor.run()` for every call, success or failure — write-once, same audit-table pattern as `RetrievalTrace`/`AIRequestLog`.

Verification: `pnpm build`/`pnpm lint` clean; new `verify:tools` (25 checks — registry/lookup/backward-compatibility/permission enforcement/agent-allowlist enforcement/execution logging), `verify:postgres-tool` (17 checks — table inspection, every write/DDL shape rejected, a real scoped `COUNT(*)`), `verify:github-tool` (17 checks — repository/branches/files/commits/PRs/issues against a mock GitHub server, ownership, agent allowlist), `verify:filesystem-tool` (15 checks — read/list/search, path-traversal rejection, no write surface), `verify:tool-calling` (12 checks — Copilot automatic tool selection for all 3 example flows plus backward compatibility) all pass against a live dev server. Full regression sweep (`verify:ai-foundation` through `verify:memory`, plus the legacy `verify:copilot`/`verify:agents`/`verify:discovery`/`verify:knowledge`/`verify:jobs`) re-run and passes unchanged.

Explicitly out of scope / deferred (per spec): a real, non-mock web search provider; a manual/HTTP `POST /ai/tools/execute` route (every new tool is reachable in-process by agents and by Copilot's automatic selection, but not directly by an external caller — `postgres_query`'s whole-database read access made a public route a deliberate scope decision to defer, not an oversight); write-capable tools of any kind (the permission model supports declaring `'write'`, but `ToolExecutor` refuses to run one); a real reranking/hybrid-search layer on top of `knowledge_search`; and any further AI agent phase.

### Phase 25 — Planning, Reflection & Self-Correction (complete)
Upgrades EstateAI from a tool-using multi-agent platform into a reasoning-first one: a `GoalPlanner` that decomposes a free-form goal into a richer `ReasoningPlan` (steps/required agents/required tools/complexity/duration/confidence estimates), a `Critic` that scores agent/plan/execution quality, a `ReflectionEngine` that synthesizes a persisted post-run report, a retry policy that only retries recoverable failures, and Plan Revision — a failed step's dependents are skipped live, in the same run, rather than failing outright.

**`GoalPlanner`** (`ai/planner/goal-planner.ts`) delegates workflow *selection* to the existing `ai/orchestrator/planner.ts`'s `Planner` (unchanged) and decorates its plain `ExecutionPlan` with the new `ReasoningPlan` fields: `requiredAgents`/`requiredTools` (drawn from Phase 24's `AGENT_TOOL_ACCESS`), `estimatedComplexity` (`LOW`/`MEDIUM`/`HIGH` by step count), `estimatedDurationMs` (longest dependency-chain depth × a documented per-step heuristic, since parallel waves don't stack), and `confidence` (a documented heuristic that decays with plan size). `revisePlan(plan, result)` drops every step that failed or transitively depends on a failed step, and recomputes those same aggregate fields around the survivors — a revision that keeps zero steps is deliberately scored at a fixed low confidence rather than the size-based heuristic (a plan that accomplishes nothing must not score well just for being small; this was a real bug caught by `verify-planner.ts` and fixed before shipping).

**Plan Revision happens live, inside one `WorkflowEngine.run()` call** — `reasoning-orchestrator.ts`'s `buildAdaptiveDefinition()` wraps every step with a dependency into a `condition` that requires every dependency to have actually *succeeded* in `context.agentOutputs` so far (composed with whatever `condition` the base `WorkflowDefinition` already declared). `WorkflowEngine` itself is unmodified — this is the existing condition/skip mechanism from Phase 17, used to a new end. `GoalPlanner.revisePlan()` is then called afterward purely for *explainability* (to persist what happened as a plan), not to trigger a second execution.

**`Critic`** (`ai/critic/critic.ts`) evaluates step/plan/execution quality independently of whether `WorkflowEngine` itself reports `SUCCESS`/`PARTIAL`/`FAILED` — a step can be `SUCCESS` (no exception thrown) yet still draw a `WARNING` finding for returning no usable evidence (an output whose only array field(s) are empty, the same heuristic Phase 24's Copilot `summarizeToolOutput()` uses). `aggregateConfidence()` (`ai/critic/confidence.ts`) blends tool success ratio, per-step agent confidence, retrieval confidence, and the Critic's own score into one overall number, with a documented neutral fallback (0.7) for any signal that wasn't available for a given run.

**`ReflectionEngine`** (`ai/reflection/reflection.engine.ts`) runs once after every reasoning-orchestrated execution and produces a persisted `ReflectionReport`: succeeded/failed/skipped steps, missing evidence (from `Critic`), weak recommendations (`recommendation-agent` output with an empty `recommendations` array), incomplete reports (`report-agent` output with an empty `sections` array), the Critic score, the aggregated overall confidence, and a plain-language `notes` trail (workflow chosen, steps that failed/were skipped, whether the plan was revised and why) — the explainability record the spec asked for.

**Retry Policy** (`ai/utils/retry-policy.ts`) — `classifyError()`/`isRetryableError()` default to `RECOVERABLE` for any ordinary `Error` (preserving every pre-Phase-25 retry behavior unchanged) and classify a small named set — `UnauthorizedError`/`ForbiddenError`/`InvalidCredentialsError`/`InvalidRefreshTokenError`/`RefreshTokenReuseError`/`ValidationError`/`ZodError`, plus a permission/validation/auth message pattern — as `PERMANENT`, never retried. Wired into `workflow.engine.ts`'s existing `isRetryable` callback with one additional `&&` clause; verified with a real recoverable-vs-permanent WorkflowEngine run in `verify-retry.ts` (a `ForbiddenError`-named failure is attempted exactly once, never retried, while a generic transient `Error` is retried to `maxAttempts` exactly as before).

**`ReasoningOrchestrator`** (`ai/planner/reasoning-orchestrator.ts`) is the new composition — `plan (GoalPlanner) -> execute (WorkflowEngine, adaptive definition) -> critique (Critic) -> revise (GoalPlanner.revisePlan, for explainability) -> reflect (ReflectionEngine) -> persist (PlanStore/ReflectionStore, Redis-backed like `ExecutionHistory`)` — a deliberately parallel, additive entry point. It does not replace or modify `OrchestratorService`/`Executor` (`POST /ai/orchestrator/execute` is untouched and still runs the plain, non-adaptive path); `POST /ai/planner/plan` is the new entry point, and it both plans and runs a goal in one call, since `GET /ai/reflection/:executionId` needs a completed execution to report on.

**New API surface**: `POST /ai/planner/plan` (plans + runs a goal, returns `{plan, finalPlan, result, critic, reflection}`), `GET /ai/planner/:id` (fetch a persisted `ReasoningPlan` by id, 404 if unknown), `GET /ai/reflection/:executionId` (fetch a persisted `ReflectionReport`, 404 if unknown) — all in `routes/planner.ts`, following the same zod-validated-body/local-error-mapper shape every other route file already uses.

Verification: `pnpm build`/`pnpm lint` clean; new `verify:planner` (20 checks — plan creation/complexity/duration/confidence, PlanningError passthrough, revision drops doomed steps but keeps independent survivors), `verify:critic` (17 checks — per-severity findings, plan-quality findings, execution scoring, confidence aggregation), `verify:reflection` (16 checks — a clean run, a partial/revised run, weak-recommendation/incomplete-report detection, PlanStore/ReflectionStore round-trips via `InMemoryStore`), `verify:retry` (9 checks — classification plus a real WorkflowEngine recoverable-vs-permanent run), `verify:planning` (20 checks — an in-process Plan Revision proof with a genuinely-throwing fake agent, since the real Discovery Agent swallows a bad GitHub credential into a graceful low-confidence `SUCCESS` rather than throwing; plus a live-server HTTP run of `POST /ai/planner/plan`/`GET /ai/planner/:id`/`GET /ai/reflection/:executionId` and a backward-compatibility check against `POST /ai/orchestrator/execute`) — all pass. Full regression sweep (`verify:ai-foundation` through `verify:tool-calling`) re-run and passes unchanged.

Explicitly out of scope / deferred (per spec): an LLM-driven planner (goal decomposition stays deterministic keyword matching, same limitation `ai/orchestrator/planner.ts` already had); a genuinely dynamic re-planning loop that inserts *new* steps or agents mid-run (Plan Revision only ever removes doomed steps, never adds alternatives); persisting/exposing per-step retry counts on `ReflectionReport` (only pass/fail/skip, not attempt counts, are surfaced there today — `AgentTaskResult.attempts` is already in the raw `ExecutionResult` if a caller wants it); and any further AI agent phase.

### Phase 26 — Human-in-the-Loop (HITL) & Approval Workflows (complete)
Upgrades EstateAI with approval gates, human review, and resumable execution: an `ApprovalEngine`/`ApprovalPolicy`/`ApprovalStore` audit trail, and a `HitlOrchestrator` that pauses a workflow at a MANUAL-decision step (`WAITING_FOR_APPROVAL`), resumes only the steps that just became unblocked once a reviewer decides (never re-invoking an agent whose step already succeeded), and supports rejection and cancellation — all built on top of the existing `WorkflowEngine`/`OrchestratorService`, neither of which is replaced or modified in its own public behavior (one additive line in `workflow.engine.ts` from Phase 25's retry policy is the only prior change to that file; Phase 26 adds nothing further to it).

**`ApprovalPolicy`** (`ai/approval/approval-policy.ts`) is a mutable registry (`register()`/`decideForAgent()`), not a fixed lookup table — no agent ships a `MANUAL` policy by default (no destructive/write-capable action exists yet, per Phase 24's scope: `ToolExecutor` still refuses to run any tool declaring `'write'`), so `register()` is what a future write-capable agent/tool would call to declare itself `MANUAL` without editing this file. Defaults: read-only agents (Discovery/Risk/Compliance/Report/Copilot) are `NEVER` gated — identical to their pre-Phase-26 behavior; Recommendation Agent is `AUTO` (an audit record is created and immediately self-approved, matching the spec's own "Low-risk recommendation -> AUTO" example). `decideForToolPermissions(permissions)` is the Phase 24 spec's own forward-looking integration point (spec #7): a `'write'` permission maps to `MANUAL`, everything else to `NEVER` — infrastructure for a future write tool, not exercised by any real call today.

**`ApprovalEngine`/`ApprovalStore`** (`ai/approval/`) — the audit trail (spec #8): every `ApprovalRequest` (`executionId`/`planId`/`workflowId`/`stepId`/`agentId`/`decision`/`status`/`reason`/`requestedAt`/`decidedBy?`/`decidedAt?`/`decisionReason?`/`comment?`/`editedOutput?`) is persisted via the same Redis-backed `MemoryStore` pattern `PlanStore`/`ReflectionStore` already use (30d TTL, longer than Phase 25's 7d — an audit trail is meant to outlive the run it describes). An `AUTO`-decision request self-approves inside `requestApproval()` itself (`decidedBy: 'system'`); a `MANUAL` one stays `PENDING` until a reviewer calls `decide()`, which supports approve/reject, a reviewer `comment`, and an `editedOutput` (spec #5's "Edit recommendation").

**Pause and resume reuse `WorkflowEngine`'s existing `condition` mechanism — the exact trick Phase 25's Plan Revision already established, extended to a new purpose.** `HitlOrchestrator.run()` requests an approval for every step whose policy isn't `NEVER`, then builds a "gated" `WorkflowDefinition` (`buildGatedDefinition()`) where a step currently `HOLD` (pending) or `BLOCKED` (rejected) gets a `condition` that returns `false`, and a dependent step's `condition` still requires its dependency to have actually *succeeded* — so a step downstream of a still-pending or rejected step is `SKIPPED`, not run, in the same call. If anything is left `HOLD` after that one pass, the overall result is `WAITING_FOR_APPROVAL`, and enough state is persisted (`PausedExecutionStore` — the plan, the `OrchestrationContext`, every step's outcome so far, and the `stepId -> ApprovalRequest id` map) to resume later. `resume()` re-derives every step's gate fresh from the current `ApprovalRequest` status and runs another pass of the same gated definition — a step already recorded as `SUCCESS` gets a `condition` that returns `false` too, so **the agent that already ran is never invoked again**; only the newly-unblocked steps (and their now-unblocked dependents) actually execute. Outcomes are merged across rounds rather than replacing the whole step list, so a multi-round resume (approve one gated step, resume, approve another, resume again) never loses an earlier round's real result.

**Status vocabulary** — `HitlRunStatus` (`WorkflowStatus | 'WAITING_FOR_APPROVAL' | 'RESUMED' | 'REJECTED'`) is `HitlOrchestrator`'s own type, not a change to `ai/orchestrator/types.ts`'s `WorkflowStatus` (which `WorkflowEngine`/`ExecutionResult`/`StateManager` all still use unchanged). `REJECTED` is derived from an explicit per-round `rejectedStepIds` list computed at the moment each step's gate is read (not re-inferred from array lengths afterward) — an earlier draft conflated "gate forced `BLOCKED` because a reviewer rejected it" with "gate forced `BLOCKED` because we just injected the reviewer's edited output instead of running the agent," which silently mis-reported a clean edited-output resume as `REJECTED`; caught and fixed by `verify-resume.ts` before shipping (see the bug note below). `RESUMED` marks a `resume()` call that reached a clean terminal state (distinct from a fresh `run()`'s `COMPLETED`, so a caller can tell whether a result came from the original pass or a later approval).

**Manual feedback** (spec #5) — a reviewer's `POST /ai/approval/:id/approve` body can carry `reason`/`comment`/`editedOutput`; when `editedOutput` is present, `HitlOrchestrator` records it directly as the step's `SUCCESS` output (`recordAgentOutput` + a synthetic `AgentTaskResult`) and the agent's own `execute()` is never called for that step at all — verified in `verify-resume.ts` by asserting the agent's own call counter stayed at zero.

**New API surface** (`routes/approval.ts`): `POST /ai/approval/request` (plans and runs a goal — same "no separate execute step" shape Phase 25 established — gating on `MANUAL` steps as needed), `POST /ai/approval/:id/approve` / `POST /ai/approval/:id/reject` (records the decision, then automatically calls `resume()` and returns `{approval, execution}`), `GET /ai/approval/:id`, `GET /ai/approval/pending`. `POST /ai/planner/plan` (Phase 25) and `POST /ai/orchestrator/execute` (Phase 17) are both completely untouched and still run their plain, ungated paths.

Verification: `pnpm build`/`pnpm lint` clean; new `verify:approval` (24 checks — policy defaults/registration, AUTO self-approval, MANUAL pending, decide()'s approve/reject/comment/edit fields, double-decide and unknown-id rejection, `listPending()`), `verify:hitl` (14 checks — a MANUAL step pauses the workflow at `WAITING_FOR_APPROVAL` with its dependent left `SKIPPED` and never invoked; approve -> resume runs both; reject -> resume runs neither; a live-server HTTP backward-compatibility check against the unchanged planner/orchestrator routes), `verify:resume` (15 checks — two independent `MANUAL` steps decided one at a time across three resume rounds, asserting the already-approved step's agent is never called a second time; an edited-output resume; `cancel()`), `verify:audit` (20 checks — every `ApprovalRequest` audit field populated and persisted across a real approve, plus the live `/ai/approval/*` routes' 404/400 handling) — all pass. Full regression sweep (`verify:ai-foundation` through `verify:planning`, all 21 prior-phase scripts) re-run and passes unchanged.

Two real bugs found and fixed during this phase's own verification, both in `hitl-orchestrator.ts`: (1) `resume()` originally re-derived each step's `ApprovalRequest` via `ApprovalStore.listPending()`, which by definition excludes any request that has already been decided — so the moment a request was rejected (or approved), it silently fell out of the "pending" list and `resume()`'s lookup found nothing, defaulting that step's gate back to `RUN` as if it had no policy at all (a rejected step would have run anyway). Fixed by persisting the `stepId -> ApprovalRequest id` map once in `PausedExecutionState` at the initial `run()` and reusing it unchanged on every `resume()`, instead of re-deriving it. (2) The gate value `'BLOCKED'` was overloaded for two different reasons — a real reviewer rejection, and "we just injected this step's edited output, don't also let the engine run it" — and `rejectedStepIds` was computed by re-scanning the gate map after both had already collapsed to the same value, so a clean edited-output resume was mis-reported as `REJECTED`. Fixed by recording `rejectedStepIds` at the moment each step's *true* gate is read, before the edited-output path can overwrite it.

Explicitly out of scope / deferred (per spec): no real write-capable tool/agent exists yet to exercise `MANUAL` gating for real (Phase 24 still refuses any tool declaring `'write'`) — every `MANUAL`-path verify check uses a synthetic in-process fake agent via `ApprovalPolicy.register()`, since no live HTTP path can produce a genuine `PENDING` request today; a `(executionId, stepId)` index on `ApprovalStore` (today's `listPending()` plus a linear scan is the only non-single-id lookup, fine at this project's scale); a durable (non-Redis-TTL) archive for old approval requests; and any further AI agent phase.

### Phase 27 — LangGraph as the Primary Agent Execution Engine (complete)
Introduces the official `@langchain/langgraph` package as an additive execution engine alongside `WorkflowEngine` — every existing agent, API, and orchestrator is untouched; LangGraph nodes *wrap* the six existing `OrchestratorAgent`s rather than reimplementing any of them.

- **`ai/langgraph/state.ts`** — `GraphStateAnnotation`, a strongly typed `Annotation.Root` carrying every field the spec asked for (goal/intent/messages/asset/connectedAccounts/discovery/risk/compliance/recommendations/report/knowledge/memory/toolResults/reflection/approval/executionTrace/metadata), plus `metadata` doubling as the plumbing bag (executionId/user/organization/planId/workflowId/conversationId) every node needs to build a real `OrchestrationContext`. `executionTrace` mirrors `AgentOutputEntry[]` exactly (the graph-native equivalent of `context.agentOutputs`) — no hidden globals; every node reads/writes only through this schema.
- **`ai/langgraph/nodes.ts`** — `makeAgentNode()` wraps one `OrchestratorAgent`: skip if already attempted to a terminal outcome (idempotent replay), gate on `ApprovalPolicy` exactly like Phase 26's `HitlOrchestrator` but pausing via LangGraph's own `interrupt()`/`Command` primitives instead of condition-based gating, then call `orchestratorAgentRegistry.get(agentId).execute(...)` — the exact call `WorkflowEngine.runStep()` makes. `discoveryNode`/`riskNode`/`complianceNode`/`recommendationNode`/`reportNode`/`copilotNode` are the six pre-built wrappers; `reflectionNode` runs Phase 25's `Critic`+`ReflectionEngine` as the graph's real last node before `END` (LangGraph has no literal post-`END` hook), persisting into the *same* `ReflectionStore` Phase 25's `GET /ai/reflection/:executionId` already reads.
- **`ai/langgraph/edges.ts`** — pure routing predicates (`hasDiscoveredResources`, `riskScoreExceedsThreshold`) reading already-computed agent output, never recalculating anything.
- **`ai/langgraph/graph-builder.ts`** — `buildWorkflowGraph(definition)` converts *any* registered `WorkflowDefinition` into a compiled graph generically (one node per step via a mutable `agentId -> node` registry mirroring `orchestratorAgentRegistry`'s own shape, a static edge per `dependsOn`), which is what makes every pre-existing workflow (`full-security-analysis`, `risk-only`, `compliance-only`, `discovery-recommendation`, `risk-recommendation`) runnable through LangGraph with zero per-workflow hardcoding — `full-security-analysis`'s own shape (Risk and Compliance both depending only on Discovery) already gives real, concurrent LangGraph execution within one Pregel superstep, satisfying "parallel execution" for free. `buildConditionalGraph()` is a second, hand-built demo graph (`security-conditional`) using genuine `addConditionalEdges` value-based routing matching the spec's own diagram (Discovery's resource count decides whether Risk runs; Risk's score decides whether Compliance runs).
- **`ai/langgraph/graph.ts`** — `graphRegistry` (lazy build-and-cache per graphId — required, not just an optimization, since a compiled graph's `MemorySaver` checkpointer must be the same instance across `run()`/`resume()` for interrupt/resume to work) and `resolveGraphId()` (keyword routing to the conditional demo graph, otherwise the workflow `ai/orchestrator/planner.ts` already resolved — same "not an AI call" spirit as every other intent-matching in this codebase).
- **`ai/langgraph/executor.ts`** — `GraphExecutor` (composition root, `graphExecutor` singleton): `run()` plans (`GoalPlanner`, unchanged), resolves/builds the graph, and `invoke()`s it on a thread keyed by `executionId`; `resume()` re-derives the live approval decision for whatever the graph is currently paused on and hands it back via `Command({resume})`, or — if this process's in-memory `MemorySaver` has nothing for that thread (a real restart) — replays the durable checkpoint back in as a fresh input on the same thread, relying on every node's idempotent replay guard to fast-forward past already-completed work.
- **`ai/langgraph/graph.checkpoint.ts`** — `GraphCheckpointStore`, a durable, Redis-backed snapshot (`{executionId, graphId, values, next, pendingApprovals, updatedAt}`) taken after every `invoke()`, following the exact same `MemoryStore`/JSON convention every other store in this codebase already uses — deliberately does *not* attempt to serialize LangGraph's own internal `Checkpoint` format; `GraphState` is plain, JSON-safe domain data by construction, so this is sufficient without reimplementing `BaseCheckpointSaver`'s chaining semantics.
- **`ai/langgraph/graph.memory.ts`** — wires Phase 16's `ConversationMemory`/`SessionMemory` and Phase 23's `KnowledgeStore` into the graph, verbatim, no duplicate memory implementation.
- **`ai/langgraph/graph.telemetry.ts`** — `estateai_ai_langgraph_*` Prometheus metrics: runs total (by graphId/status), duration, nodes visited, a structural "widest parallel wave" gauge, checkpoints persisted, and retries (via LangGraph's own official per-node `RetryPolicy.retryOn`, reusing `ai/utils/retry-policy.ts`'s classifier unchanged).
- **New API surface** (`routes/langgraph.ts`): `POST /ai/langgraph/execute` (plans+runs a goal, same "no separate execute step" shape Phase 25/26 established), `POST /ai/langgraph/:executionId/resume` (continues a paused graph — a reviewer decides via the *existing*, unchanged `POST /ai/approval/:id/approve|reject` first), `GET /ai/langgraph/:executionId`, `GET /ai/langgraph/:executionId/state`.

**Real bugs found and fixed during this phase's own verification** (in order caught):
1. **Node names colliding with state channel names.** LangGraph forbids a node name identical to a state field name, and `workflowRegistry`'s own stepIds (`discovery`/`risk`/`compliance`/`report`) are exactly four of `GraphState`'s channel names — every graph node is now registered under a `-node`-suffixed name; `dependsOn` bookkeeping keeps using the plain stepId everywhere else.
2. **`invoke()`'s return value can be `undefined`.** A round where every node's return is an empty patch (e.g. a fully idempotent replay with nothing left to do) can leave `compiledGraph.invoke()` resolving `undefined` — `GraphExecutor` now always reads the authoritative final state from `compiledGraph.getState()` instead of trusting `invoke()`'s own return.
3. **A static `addEdge(dep, step)` doesn't skip a dependent when its dependency was rejected or failed** — LangGraph runs `step`'s node the moment `dep`'s node *completes*, regardless of outcome, unlike `WorkflowEngine`'s `condition`-based dependency-success gating. `buildWorkflowGraph()` now wraps every node with `withDependencyGate()`, which checks `executionTrace` for a `SUCCESS` entry per `dependsOn` id before ever calling the real node, recording a `SKIPPED` entry otherwise — caught via a MANUAL-gated step's rejected downstream dependent still running.
4. **The idempotent-replay guard only checked `state[stateKey] !== undefined`**, which a `FAILED` attempt never sets (only `SUCCESS` does) — a "resume after restart" replay silently re-invoked an agent that had already failed. The guard now checks `executionTrace` for *any* terminal (`SUCCESS` or `FAILED`) entry for that step, not just its output slot.

Full regression sweep (`verify:ai-foundation` through `verify:audit`, 26 scripts) re-run against the live server and passes unchanged.

Example execution: `POST /ai/langgraph/execute {"goal": "full security analysis"}` resolves to the `full-security-analysis` graph; Discovery runs, then Risk and Compliance run in the same superstep (genuinely concurrent, not just fast-sequential), then Recommendation (`AUTO`-approved per `ApprovalPolicy`, self-resolves inline) and Report, then Reflection persists a `ReflectionReport` — `GET /ai/reflection/:executionId` (Phase 25's own route) reads it back unchanged. If a step's `ApprovalPolicy` decision were `MANUAL`, the graph would instead pause at `WAITING_FOR_APPROVAL`; a reviewer calls `POST /ai/approval/:id/approve`, then `POST /ai/langgraph/:executionId/resume` continues from exactly where it paused — including correctly, after a real process restart, since the durable checkpoint plus every node's idempotent replay guard fast-forward past whatever already finished.

### Phase 29 — Multi-Agent Debate & Consensus (complete)
Adds a debate/consensus layer where four *existing* agents (Risk/Compliance/Recommendation/Copilot) each run their own unmodified analysis over the same asset, and a new, independent layer cross-checks the results for structural disagreement before accepting them — no agent modified, no business logic duplicated, no agent output ever mutated by another. Every participant call is `orchestratorAgentRegistry.get(agentId).execute(...)`, identical to every other execution engine (`WorkflowEngine`, LangGraph, the LLM Planner) already in place, all of which remain completely untouched.

- **`ai/debate/debate.engine.ts`** — `DebateEngine.run()`: Risk Agent runs first, then Recommendation Agent (its own existing cross-referencing logic already reads Risk's just-recorded output from the shared `OrchestrationContext`), then Compliance Agent. `evaluateTrigger()` (spec #5) checks average confidence < 0.6, a detected structural disagreement, or risk ≥ HIGH; if none apply, the debate stops there — "execution continues normally," the three analytical outputs still returned. If triggered, Copilot Agent runs with a message its own existing `SUMMARIZE_REPORT` intent path handles (no new business logic), then `ConsensusEngine` computes the final report.
- **`ai/debate/consensus.scoring.ts`** — pure, deterministic heuristics: `classifyFindings()` (a Risk finding is "accepted" only if a Recommendation actually cites it), `computeAgreementScore()`, `deriveConflicts()` (four structural cross-checks, shared verbatim between the trigger check and the final `ConsensusReport`), `computeConsensusConfidence()`.
- **`ai/debate/consensus.engine.ts`/`consensus.ts`** — `ConsensusEngine` assembles a `ConsensusReport` (agreement score, confidence, conflicts, accepted/rejected findings, reasoning summary — spec #4); `ConsensusStore` persists it (Redis-backed, same pattern every prior store uses).
- **`ai/debate/debate.memory.ts`/`debate.telemetry.ts`** — `DebateMemory` (get/set-by-id + per-asset history, spec #7); `estateai_ai_debate_*` Prometheus metrics (duration, participants, messages, agreement %, confidence delta — spec #8).
- **`ai/reflection/reflection.types.ts`/`reflection.engine.ts`** (modified, additive) — `ReflectionReport` gained optional `debateSummary?`/`disagreements?`/`consensusConfidence?` fields, populated only when `ReflectionEngine.reflect()` is called with a new optional `DebateReflectionSummary` parameter; every existing call site is unaffected. `DebateEngine` calls this to produce a debate's own reflection, persisted into the same, unchanged `ReflectionStore` — `GET /ai/reflection/:executionId` already reads it back using the `debateId`.
- **New API surface** (`routes/debate.ts`): `POST /ai/debate/start`, `GET /ai/debate/:id`, `GET /ai/consensus/:id`.

No real bugs were found during this phase's own verification — build and lint were clean on the first pass, and all six new verify scripts passed on their first run.

Verification: `pnpm build`/`pnpm lint` clean; new `verify:debate` (a full triggered debate end to end, Reflection Integration, and telemetry registration), `verify:consensus` (every `consensus.scoring.ts` heuristic exercised directly), `verify:agent-review` (spec-#3 call order, critique labeling, and confirmation that no participant output is ever mutated), `verify:disagreement` (each of the three trigger conditions exercised independently, plus the not-triggered path), `verify:consensus-memory` (`DebateMemory`/`ConsensusStore` round-trips), `verify:debate-routing` (the live `/ai/debate/*`+`/ai/consensus/*` routes, 401/404/400 handling, and backward compatibility against every pre-existing AI entry point) — all pass. ### Phase 30 — Long-Term Episodic Memory & Continuous Learning (complete)
Adds a persisted "episode" per completed execution — goal/plan/agents/tools/debate/consensus/reflection/duration/failures/retries/approvals/outcome/confidence, plus deterministically derived lessons (What Worked/What Failed/Lessons Learned/Future Suggestions) — indexed into the *existing* Knowledge Store/Retrieval Service (no second vector database) and read back by the LLM Planner before it plans, so a new goal on the same asset is planned with the memory of what happened last time. Existing planner, RAG, LangGraph, and reflection engine all keep their own public behavior unchanged; every new piece is additive.

- **`ai/episodic-memory/episode.extractor.ts`** — `EpisodeExtractor.capture()`: turns an `ExecutionResult` (+ whatever a call site also has on hand: plan/criticReport/reflection/debate/consensus) into a persisted, indexed `Episode`. Called via the fire-and-forget `captureEpisodeSafely()` wrapper (mirrors Phase 23's `indexAgentOutput` precedent — capture must never delay or fail the execution it's observing) from all four "completed execution" sites in the codebase: `planner/reasoning-orchestrator.ts`, `langgraph/nodes.ts`'s `reflectionNode`, `debate/debate.engine.ts` (both the triggered and not-triggered paths), and `orchestrator/executor.ts` (the plain, non-reasoning path).
- **`ai/episodic-memory/episode.summary.ts`** — `deriveLessons()`: deterministic, heuristic derivation of Lessons Learned/What Worked/What Failed/Future Suggestions straight from data every execution already produces (`ExecutionResult.steps`, `ReflectionReport`, `DebateRecord`, `ConsensusReport`) — no new LLM call, no modification to `ReflectionEngine` itself.
- **`ai/episodic-memory/episode.indexer.ts`/`episode.search.ts`** — episodes are indexed into the *existing* `KnowledgeStore` under a new `documentType: 'EPISODE'` (added to the `KnowledgeDocumentType` Postgres enum via an additive migration) and searched via the *existing* `RetrievalService`; a hit is resolved back to its full `Episode` via `KnowledgeDocument.sourceId === episode.episodeId`.
- **`ai/episodic-memory/episode.store.ts`/`episode.pruner.ts`** — `EpisodeStore` follows the same injected-`MemoryStore`/Redis pattern as every Phase 25+ store (`DebateMemory`, `ConsensusStore`), but keeps history lists as a rewritable JSON array (not a Redis list) so `EpisodePruner` can remove arbitrary ids — a max-count cap per asset, with an optional "archive" mode that keeps a compressed summary (goal/outcome/confidence/lessons only) for 30 days after the full episode is pruned.
- **`ai/episodic-memory/episode.relevance.ts`** — `computeAgentReliability()`/`computeToolReliability()` (success rate, average confidence/latency, aggregated from stored episodes) and `calibrateConfidence()` (a weighted blend of a planner's base confidence with historical success rate/similarity/agent/tool reliability, degrading gracefully to the base confidence when no history exists).
- **Planner Integration** (`llm-planner/planner.types.ts`/`planner.memory.ts`/`planner.prompt.ts`, modified, additive) — `PlannerContextSummary` gained an `episodeSummary` field, populated by a new `summarizeEpisodes()` that calls `EpisodeSearch.search()` for the current goal/asset and surfaces the top matches' outcomes and lessons directly into the LLM Planner's prompt.
- **New API surface** (`routes/episodes.ts`): `POST /ai/episodes/search`, `GET /ai/episodes/:id`, `GET /ai/episodes/history`, `GET /ai/episodes/statistics`.

One real bug was found and fixed during this phase's own verification: `episode.telemetry.ts` transitively imports `observability/metrics.ts` → `workers/worker-pool.ts` → `workers/worker.ts`, which imports the real `redis` singleton and connects on import — the same pre-existing chain that makes `verify:jobs` hang. `verify-episodes.ts` (the first Phase 30 script to import `episodeTelemetry`) hung on process exit until `redis.quit()` was added in its `.finally()`, the same fix every Phase 29 telemetry-using verify script already carries.

Verification: `pnpm build`/`pnpm lint` clean; new `verify:episodes` (pure `EpisodeExtractor`/`EpisodeStore` unit test — field derivation, indexing, get/history round trip, no-assetId path), `verify:learning` (runs a real reasoning-first execution and confirms the captured episode's lessons are derived from that *same run's* real `ReflectionReport`, not a fixture), `verify:memory-retrieval` (real Postgres/pgvector + Redis: index two episodes, confirm semantic ranking, cross-asset isolation, and that `gatherPlannerContext` surfaces the match), `verify:confidence-calibration` (`calibrateConfidence`/`computeAgentReliability`/`computeToolReliability` against fixtures), `verify:pruning` (max-count eviction, archive mode, compression, non-archive mode), `verify:history` (the live `/ai/episodes/*` routes, 401/404/400 handling, and backward compatibility against every pre-existing AI entry point) — all pass. Full regression sweep (all 82 `apps/api` `verify:*` scripts) re-run against the live server.

Example execution: an execution completes anywhere in the system → an `Episode` is captured and indexed automatically, no manual call → `POST /ai/episodes/search {"goal": "...", "assetId": "..."}` finds it by semantic similarity → the next `POST /ai/planner/plan` or `POST /ai/planner/dynamic` for a similar goal on the same asset includes that episode's outcome and lessons in its own prompt via `episodeSummary`.

Explicitly out of scope / deferred (per spec): confidence calibration and tool reliability are exposed as plain functions over stored episodes, not wired into any agent's live decision-making (no existing "tool selector" beyond Copilot's own stateless regex classifier exists to wire into); per-agent confidence isn't retained on the episode (only the whole-execution confidence), so `computeAgentReliability()`'s "average confidence" is coarser than a true per-agent score; TTL expiry itself isn't exercised by a verify script (nothing waits out a 7-day Redis TTL); pruning must be triggered explicitly (`EpisodePruner.pruneAsset()`), there is no background job that runs it automatically yet.
