# Architectural Decisions

Additive or non-obvious decisions made during implementation that weren't explicitly dictated by a spec, kept here so future work understands the *why* without re-deriving it. Ordered roughly by when each was made.

---

### Soft-reference (no FK) for `SyncJob.accountId`/`assetId`, `Resource.accountId`/`assetId`, `Relationship.fromResourceId`/`toResourceId`, `Finding.resourceId`, `Recommendation.findingId`, `RiskScore.assetId`/`accountId`/`resourceId`, `Policy`-referencing `PolicyResult.policyId`/`resourceId`/`findingId`
**Decision**: these fields are plain `String` columns, not Prisma `@relation`s.
**Why**: avoids cascade-delete complexity and avoids coupling these tables' lifecycles to `Asset`/`Account`/`Resource`/`Finding`/`Policy` row deletion — deleting an asset must never be blocked by, or silently cascade into, job history, graph edges, findings, risk history, or policy results. Also avoids touching the `Asset`/`Account`/`Resource`/`Finding`/`Policy` models' own field lists to add back-relations.
**Tradeoff accepted**: referential integrity for these fields is enforced only at the service layer (via `getOwnedAsset`/`getOwnedAccount`/`getOwnedResource`), not the database. An orphaned soft-reference is possible in theory (e.g. a `SyncJob` pointing at a deleted account, or a `Finding`/`PolicyResult` pointing at a hard-deleted `Resource`) but harmless — it's read-only historical/graph/analysis data, not something that needs to stay consistent for correctness. Confirmed in practice at Phase 6A/6B: several older verification scripts (`verify-discovery.ts`, `verify-sync.ts`, `verify-jobs.ts`) hard-delete `Resource` rows in cleanup without knowing `Finding`/`RiskScore`/`PolicyResult` rows now exist, and this causes no failures — only harmless orphaned rows (see [TODO.md](TODO.md)).

### `Resource` identity is global `(provider, providerResourceId)`, not scoped per account/asset
**Decision**: two different accounts discovering "the same" GitHub repo (e.g. a repo they both have access to) resolve to the same `Resource` row; rediscovery by a different account shifts `accountId`/`assetId` to the most recent discoverer.
**Why**: this was the literal Phase 5A spec requirement, not an inference.
**Consequence reasoned through during Phase 5A**: `ResourceService.persist()`'s soft-delete diff pass scopes "previously active" resources via `findActiveByAccount(accountId)`. If a resource's `accountId` shifts to a different account, it simply drops out of the original account's active set on that account's next discovery run — it does not get spuriously soft-deleted, because the diff pass only fires for resources still attributed to the *current* discovering account that went missing from *this batch*. No cross-account correctness issue exists despite the shared-identity design.

### `Relationship` unique constraint on `(fromResourceId, toResourceId, relationshipType)`
**Decision**: additive, not explicitly requested by the Phase 5B spec.
**Why**: prevents duplicate edges from being created on every rediscovery run — without it, re-running discovery against an unchanged graph would either need extra application-level dedup logic or would accumulate duplicate rows.
**How to apply**: any new relationship extractor can rely on `upsert` being idempotent per edge identity; no extractor needs its own dedup logic.

### `JobPriority` declared ascending (`LOW, NORMAL, HIGH, CRITICAL`)
**Decision**: enum values declared in ascending priority order.
**Why**: Postgres enums compare by declaration order, and the job-claiming query needs `ORDER BY priority DESC` to surface `CRITICAL` jobs first. Declaring ascending makes `DESC` mean "most urgent first" without a `CASE` expression or a separate integer column.

### Redis is a fast-path signal only, not the job queue's source of truth
**Decision**: `RPUSH` on enqueue, non-blocking `LPOP` checked each poll tick; Postgres (`SyncJob` + status-guarded `UPDATE ... WHERE id=? AND status=?`) is the actual queue and locking mechanism.
**Why**: keeps exactly-once claim semantics durable and race-safe without depending on Redis's availability or any distributed-lock library — if Redis is down or a push is missed, the `JOB_POLL_INTERVAL_MS` fallback still finds the job. Redis only makes the common case faster, never more correct.

### Free-form strings for `JobType`, `Account.provider`, `Relationship.relationshipType`; real enums for `JobStatus`/`JobPriority`
**Decision**: split based on whether the set of values is expected to grow.
**Why**: `JobType`/`provider`/`relationshipType` are meant to be extended by adding a new registry entry, never by running a migration — a Postgres enum would defeat that. `JobStatus`/`JobPriority` are closed, stable sets where DB-level validation and (for priority) declaration-order sorting are worth the migration cost of ever changing them.

### `PermanentJobError` classification imported into `JobExecutor` without modifying Sync/Discovery modules
**Decision**: `job-executor.ts`'s `isPermanentFailure()` helper explicitly recognizes `SyncProviderError` and `UnsupportedDiscoveryProviderError` (both pre-existing, thrown from their own modules) as non-retryable, in addition to `PermanentJobError` and its subclasses.
**Why**: these two errors mean "no handler exists for this provider" — retrying can never succeed, so treating them as retryable would just waste `maxAttempts` retries and delay reaching `DEAD`. Recognizing them by importing the classes (rather than making Sync/Discovery throw a `PermanentJobError` subtype) kept those modules unaware of the job system, preserving their usability outside of jobs.

### No shared cross-route error-mapping helper
**Decision**: every route file defines its own local `mapXError(err)` (or inline `instanceof` chains for the simplest routes).
**Why**: inherited pattern from before Phase 4; each domain's error set is small and mostly disjoint, so a shared mapper would mostly be a switch statement importing every error class from every domain. Not revisited as part of Phase 4/5A/5B since none of those checkpoints touched routing conventions. Worth reconsidering only if a future checkpoint adds enough routes that duplication becomes a real maintenance cost.

### `GET /oauth/:provider/callback` is unauthenticated
**Decision**: no `app.authenticate` guard on the callback route, unlike every other non-auth route.
**Why**: the browser redirect from the OAuth provider back to this callback cannot carry a bearer token header — security instead comes from the single-use, TTL'd `state` token minted before redirect and validated (and immediately invalidated) here.

### `RiskScore` has no DB-level uniqueness constraint; `RiskScoreRepository` enforces one-row-per-scope+entity at the application layer
**Decision**: `@@index([scope])`/`[assetId]`/`[accountId]`/`[resourceId]` only — no `@@unique`.
**Why**: a Postgres unique constraint treats `NULL` as distinct from every other `NULL`, so a naive `@@unique([scope, assetId, accountId, resourceId])` would not actually prevent duplicate `OVERALL` rows (all four columns null) or duplicate `ACCOUNT` rows for the same account (assetId/resourceId both null on every one) — only the one populated column would need to collide, and Postgres won't enforce that across mixed-null tuples. `RiskScoreRepository.upsert()` instead does find-then-update-or-create per scope, the same pattern already established for `Resource`'s content-addressed upsert, just without a DB constraint backing it since one isn't expressible here without four partial unique indexes.
**How to apply**: `RiskService` is the only writer of `RiskScore` rows, so this is safe — a future second writer would need to either share `RiskScoreRepository.upsert()` or the one-row guarantee breaks.

### `Recommendation.priority` reuses `FindingSeverity` rather than a separate `RecommendationPriority` enum
**Decision**: no new enum was added for recommendation priority.
**Why**: a recommendation's priority is always derived 1:1 from its finding's severity at creation time (`RecommendationService.generateForFinding` sets `priority: finding.severity` directly) — a separate enum with the same five values would be a pure duplicate with no independent meaning yet.

### `Finding`/`Recommendation` lifecycle: reopening a resolved finding does not create a new row
**Decision**: if a rule's issue reappears on a resource after being resolved, `FindingService` updates the existing `Finding` row back to `OPEN` (clearing `resolvedAt`) rather than creating a second row for the same `(resourceId, ruleCode)`.
**Why**: `@@unique([resourceId, ruleCode])` already makes "one row per rule per resource" the identity model — a second row for the same rule on the same resource would violate that identity, and would also fragment a finding's history (confidence, original creation time) across rows for what is really the same recurring issue. The same reopen-in-place behavior is mirrored for its `Recommendation` (`reopenForFinding`), for the same reason `Recommendation.findingId` is `@unique`.
**Observability note**: reopening emits `FINDING_UPDATED`, not a distinct `FINDING_REOPENED` — the Phase 6A spec's event list only names `FINDING_CREATED`/`FINDING_UPDATED`/`FINDING_RESOLVED`, and a status flip from RESOLVED back to OPEN is treated as one more kind of update rather than a sixth event type.

### `EMPTY_REPOSITORY` rule detects emptiness via GitHub's `size` field (KB pushed), not a dedicated API call
**Decision**: `metadata.size === 0` is the sole signal, sourced from the same `/user/repos` response already fetched for every other rule — no additional GitHub API request per repository.
**Why**: GitHub's own UI uses this identical signal ("this repository is empty") and it's already present on every repo object, so no extra network cost is incurred to support this rule, consistent with `contains` relationship extraction's "no extra API calls" precedent from Phase 5B.

### `Policy` is the first model with both a code registry and a database table for the same entity; `enabled` is the only field the DB owns
**Decision**: `PolicyService.ensureRegisteredPoliciesPersisted()` upserts every `policyRegistry.allMetadata()` entry into `Policy` on every evaluation run, refreshing `name`/`description`/`provider`/`resourceType`/`severity`/`conditions` — but the `update` branch of `PolicyRepository.upsertDefinition()` never includes `enabled`.
**Why**: every other registry in this codebase (rules, extractors, providers) is pure code with no DB-persisted twin — but the Phase 6B spec explicitly asked for a "Policy" table with an `enabled` field, meaning policies must be individually toggleable without a code change or deploy. If the metadata sync also overwrote `enabled` on every run, disabling a policy would only last until the next discovery call re-synced it back to `true`, defeating the entire point of the field.
**How to apply**: any future field added to `Policy` needs the same split decision made explicitly — does the code registry own it (sync every run) or does the database own it (sync never touches it)? Don't default to "sync everything."

### `PolicyEngine` takes a pre-resolved `enabledCodes: Set<string>` rather than checking `Policy.enabled` itself
**Decision**: `PolicyService.evaluateResources()` queries `policyRepository.findEnabledCodes(provider)` once per run and passes the resulting `Set` into `PolicyEngine.evaluate()`, which filters `policyRegistry.policiesFor(resource)` against it.
**Why**: mirrors `RuleEngine`'s existing constraint of never touching the database — `PolicyEngine` stays a pure, synchronous, unit-testable function of (resources, findings, enabled set) → results, with all I/O living in `PolicyService`. This also means "enabled" is resolved exactly once per evaluation run (not once per resource), which is both cheaper and guarantees every resource in one run sees the same enabled/disabled snapshot even if a policy is toggled mid-run by a concurrent request.

### `PolicyResult.status` transitions to `POLICY_PASSED`/`POLICY_FAILED` events only, not `WARNING`/`NOT_APPLICABLE`
**Decision**: `PolicyService.evaluateResources()` only emits an event when a result's status changed AND the new status is `PASS` or `FAIL`; a change to/from `WARNING` or `NOT_APPLICABLE` persists the row silently.
**Why**: the Phase 6B spec's event list only names `POLICY_PASSED`/`POLICY_FAILED`/`COMPLIANCE_UPDATED` — `WARNING`/`NOT_APPLICABLE` don't have a corresponding event type, and inventing one wasn't asked for. This mirrors the Phase 6A decision to not invent a `FINDING_REOPENED` event for a status transition the spec's event list didn't name.

### `ComplianceReport` is computed at query time, not stored as a snapshot like `RiskScore`
**Decision**: `ComplianceService.buildReport()` re-aggregates `PolicyResult`/`Finding`/`RiskScore` rows fresh on every call (`GET /compliance*` and the post-discovery `recalculateAndNotify`) — there is no `ComplianceScore` or `ComplianceReport` table.
**Why**: the Phase 6B spec's database section only listed `Policy` and `PolicyResult` as new models, unlike Phase 6A's spec which explicitly asked for a `RiskScore` table. Given that literal scope, treating compliance as a derived view over already-persisted data (rather than inventing an unrequested third table) was the more conservative reading — it also means a compliance report is never stale relative to the `PolicyResult` rows it's built from, at the cost of recomputing severity/risk distributions on every request rather than reading a cached number.
**How to apply**: if a future checkpoint needs compliance history/trends over time, that's the point where a persisted snapshot table (mirroring `RiskScore`) would become justified — today's design has nowhere to read "what was our score last week."

### Compliance score formula: `(pass + warning×0.5) / (pass + fail + warning)`, `NOT_APPLICABLE` excluded from the denominator
**Decision**: not specified by the spec, chosen deliberately.
**Why**: `NOT_APPLICABLE` means the policy had nothing to say about that resource (e.g. `FORK_REPOSITORIES_IGNORED` on a fork) — counting it in the denominator would let irrelevant policies dilute a score in either direction depending on how many "not applicable" policies happen to exist. `WARNING` (a permitted-but-flagged state, like an archived repo) is treated as half-credit rather than either a full pass or a full violation, since it's neither. The score defaults to 100 when nothing applicable was evaluated (vacuously compliant), matching `RiskService`'s "0 findings → 0 risk" convention at the opposite end of the scale.

### `riskDistribution` buckets: low <25, medium <50, high <75, critical ≥75
**Decision**: not specified by the spec, chosen deliberately, reusing the 0-100 `RiskScore.overallScore` scale from Phase 6A.
**Why**: quartile-width bands over the same 0-100 scale `RiskService` already produces — no new scoring logic, just a display-oriented grouping for the compliance report's `riskDistribution` field.

### Bug found during Phase 6B: `z.coerce.boolean()` on query params silently reads `"false"` as `true`
**Decision**: added a shared `booleanQueryParam` helper in `routes/shared/validation.ts` (`z.enum(['true','false']).optional().transform(...)`) and fixed both `routes/policies.ts` (new) and `routes/resources.ts` (pre-existing, same bug in `includeDeleted`).
**Why**: `Boolean("false")` is `true` in JavaScript — `z.coerce.boolean()` calls the `Boolean()` constructor on the raw string, so any non-empty query string coerces to `true` regardless of its content. This went unnoticed in `resources.ts` since `includeDeleted=false` and "param omitted" have the same effect (both mean "exclude deleted"), so the bug was never behaviorally distinguishable there. It was caught here because `Policy.enabled` needed `enabled=false` to behave differently from `enabled` omitted, and `verify-policy.ts`'s "policy updates" check exercises exactly that.
**How to apply**: never use `z.coerce.boolean()` for a query/form string param where both `true` and `false` are meaningful, valid inputs — only where the field is presence-only (e.g. a flag that's either omitted or `"true"`).

### `DiscoveryAgent` reads persisted resource/graph data rather than calling `DiscoveryService.discover()`
**Decision**: `DiscoveryAgent.execute()` uses `ResourceSearchService.search()` + a bounded `GraphService.neighbors()` sample instead of literally invoking `discoveryProviderRegistry`/`DiscoveryService.discover()`, even though the Phase 7A spec's own wording says the agent "uses DiscoveryService, GraphService."
**Why**: `DiscoveryService.discover()` hits the live provider API and already has a dedicated, deliberately asynchronous entry point (`POST /accounts/:id/discover`, Phase 4's job framework) precisely because it's slow and external-network-dependent. `AgentOrchestrator.execute()` runs entirely synchronously inside one HTTP request — every other agent (`RiskAgent`, `ComplianceAgent`, `RecommendationAgent`) only reads already-persisted rows for exactly this reason. Making `DiscoveryAgent` the one exception that reaches out to a live external API would reintroduce the request-blocking-on-a-third-party-call problem Phase 4 was built to eliminate, and would duplicate the job framework's responsibility rather than orchestrate it.
**Tradeoff accepted**: `DISCOVERY_SUMMARY`/`SECURITY_REPORT` reflect the asset's state as of its last completed discovery job, not a fresh live pull. There is no single request that "runs discovery, then reports on it" — a caller who wants a fresh report must first `POST /accounts/:id/discover`, poll it to completion, then call `POST /agents/execute`. This is the same two-step shape every other analysis/policy/compliance endpoint already has relative to discovery.

### Agents are orchestrated synchronously in-request, not as `SyncJob` rows
**Decision**: `AgentOrchestrator.execute()` runs the full plan to completion before `POST /agents/execute` returns — there is no `AI_DISCOVERY`/`AI_ANALYSIS`/etc. job type registered in `job-dispatcher.ts`, despite those `JobType` values having been reserved since Phase 4.
**Why**: every agent in this phase only reads data other phases already persisted (resources, findings, risk scores, policy results, compliance reports) — none of it involves a slow external call, so there's nothing here that benefits from the queue/poll/retry machinery Phase 4 built for sync and discovery. Introducing job rows for reads that complete in milliseconds would add latency (enqueue → poll `GET /jobs/:id` in a loop) without a corresponding benefit.
**How to apply**: if Phase 7B introduces an agent that calls a real LLM (meaningfully slower, possibly rate-limited), that's the point where routing it through the existing job framework — via the already-reserved `AI_*` job types — becomes the right call, not this synchronous path. The `Agent` interface itself doesn't need to change either way; only `AgentOrchestrator` would need a job-queued variant.

### `Agent.plan()` returns dependency hints; `PlannerService` never hardcodes a pipeline
**Decision**: each agent's `plan(context): AgentPlanHint` declares its own `dependsOn` (by agent id), and `PlannerService.createPlan()` builds every `AgentTask` generically from `agentRegistry.agentsFor(requestType)` + each agent's own hint — there is no `Map<requestType, AgentTask[]>` catalog anywhere in the planner.
**Why**: the spec requires "Planner must not know providers" and "Registry must be extensible." A hardcoded per-request-type task list in the planner would violate both the moment a new agent needed to slot into an existing request type (e.g. a future `CostAgent` joining `SECURITY_REPORT`) — that would mean editing the planner itself rather than just registering a new agent. Pushing dependency declarations onto each agent keeps the planner a pure function of "which agents currently support() this request type," matching the registry pattern used everywhere else in the codebase (rules, policies, sync/discovery/oauth providers).
**How to apply**: adding a 6th agent to `SECURITY_REPORT` requires only creating the agent file, declaring `supports()`/`plan()`, and adding one import line to `agents/index.ts` — no other file changes. `PlannerService` does still guard against a dangling `dependsOn` (one referencing an agent not part of the current plan) by dropping it, since an agent's `plan()` can't know in advance which other agents will be included in every request type it might be asked about.

### `ReportAgent` reads upstream results off `AgentContext`, never re-queries services directly
**Decision**: `ReportAgent.execute()` calls `context.getResult('discovery')`/`'risk'`/`'compliance'`/`'recommendation')` and reshapes those `AgentResult.data` payloads — it has no imports from `services/analysis`, `services/policy`, or `services/graph` at all.
**Why**: `ReportAgent`'s whole purpose is aggregation, not analysis — re-fetching `RiskScore`/`ComplianceReport` itself would duplicate exactly the queries `RiskAgent`/`ComplianceAgent` already ran in the same plan, defeating the "Shared Context... without duplicate queries" requirement at the one point in the pipeline where duplication would be easiest to introduce by accident (a report combining everyone else's output).
**Tradeoff accepted**: `ReportAgent` only produces a meaningful report when it runs in the same plan as its four dependencies — it's `supports()`-gated to `SECURITY_REPORT` only (never a request type where it could run standalone) specifically because of this. A dependency that failed or was skipped is treated as "section omitted," not a hard failure, so a partial upstream failure still yields a partial (not empty) report.

### `AgentPlanExecution.id` is caller-supplied (the plan's own generated id), not left to `@default(cuid())`
**Decision**: `PlannerService.createPlan()` generates the plan id (`randomUUID()`), and `AgentOrchestrator` passes that same id explicitly into `agentPlanExecutionRepository.create({ id: plan.id, ... })`.
**Why**: the plan id needs to exist before the audit row does (it's used in the `PLAN_CREATED` event's metadata and in the `AggregatedPlanResult` returned to the caller) — generating a separate DB-assigned id and mapping between the two would add a translation step for no benefit. Prisma allows an explicit `id` in `create()` data even when the field has `@default(cuid())`; the default only fires when the field is omitted.

### Bug found during this phase: `verify-agents.ts`'s mock GitHub server initially used a different port than every other verify script
**Decision**: `verify-agents.ts` now uses `MOCK_PORT = 3999`, matching `verify-sync.ts`/`verify-discovery.ts`/`verify-analysis.ts`/`verify-policy.ts`.
**Why**: the GitHub discovery provider's base URLs are fixed at config load time via `GITHUB_TOKEN_URL`/`GITHUB_USER_URL`/`GITHUB_REPOS_URL`/`GITHUB_ORGS_URL` (all `http://localhost:3999` in `.env`) — they are not parameterizable per test run. The script's first draft picked `4001` (to "avoid colliding" with other scripts, reasoning that turned out to be backwards, since scripts run sequentially and share the one fixed mock port already established by every prior phase's verification). The mismatch made the account's only discovery job fail against a `4001`-listening mock server that the provider never actually requests, and the job entered `RETRYING` on a long backoff. Several of the script's own assertions were initially too weak to catch this (checking "a data key exists" rather than "the value is non-trivial"), so the suite went green on empty data until the job-status assertion itself caught it.
**How to apply**: any future verify script exercising GitHub discovery must reuse port `3999`; there is exactly one mock port across the whole verification suite, not one per script. More generally, an assertion like "the response has this key" is weaker than "the response has this key with a plausible value" — prefer the latter for any check meant to catch an upstream pipeline silently not running.

### `AIService` was kept fully standalone in Phase 7B — no existing agent was wired to call it
**Decision**: none of Phase 7A's 5 agents (`DiscoveryAgent`/`RiskAgent`/`ComplianceAgent`/`RecommendationAgent`/`ReportAgent`) were modified this phase. `POST /ai/generate` is the only caller of `AIService.generate()` today.
**Why**: confirmed explicitly with the user before implementation began (this phase's kickoff spec's "Agent Integration" section showed the intended future call chain — `RiskAgent → RiskService → AIService.generate() → Provider` — as architectural guidance, not a mandate to implement it this phase; the spec's own "Objective" line was "Now build the AI abstraction layer," and the "STOP" section's framing ("Only implement the LLM abstraction framework... Wait for review") pointed the same way). Given the standing project rule of confirming genuinely ambiguous scope before building, this was surfaced as a direct choice rather than assumed either way.
**How to apply**: `PromptBuilder`/`AIService`/`AIProvider` needed zero design changes to leave this door open — `PromptBuilder.build()` takes plain strings/objects (`systemPrompt`, `userPrompt`, `contextBlocks`), never an `AgentContext`/`AgentResult`, specifically so a future agent integration is additive (the agent's own service calls `aiService.generate()` directly, per the spec's intended chain) rather than requiring a rework of this phase's framework. The natural Phase 7C starting point is wiring one agent (e.g. an optional AI-generated narrative section on `ReportAgent`) to prove the chain end-to-end.

### `AIProvider.generate()` returns an already-standardized `AIResponse`, not raw vendor JSON
**Decision**: unlike the spec's architecture diagram implying a separate "Response Parser" stage sitting between "AI Service" and "Provider Adapter," each provider's `generate()` calls `responseParser.normalize()` itself before returning — `AIService` never sees vendor-specific response shapes at all.
**Why**: matches the registry-pattern precedent set by every other pluggable interface in this codebase (`DiscoveryProvider.discover()` returns normalized `DiscoveredResource[]`, not raw provider JSON; `Policy.evaluate()` returns a normalized `PolicyEvaluation`, not raw resource data) — the boundary of "vendor-specific parsing" is the provider file itself, not a separate downstream stage. `response-parser.ts` still exists as a distinct file (per the spec's `DIRECTORY` list) and still does real, shared work — attaching `estimatedCostUsd`/`latencyMs` — just as a helper each provider calls internally rather than a stage `AIService` invokes after the fact.
**Tradeoff accepted**: the "Response Parser" in the architecture diagram reads as `AIService`'s responsibility; in this implementation it's closer to each provider's own last step, with the shared assembly logic factored out so it isn't tripled. This was judged truer to the codebase's established registry conventions than a literal reading of the diagram.

### Token counting is an approximation; only post-response usage figures are exact
**Decision**: `token-counter.ts`'s `estimateTokens()` is a chars/4 heuristic, not Claude's/OpenAI's/Gemini's actual tokenizer.
**Why**: each vendor's real tokenizer is a separate dependency (tiktoken for OpenAI, Anthropic's own tokenizer, SentencePiece-based for Gemini) — pulling in three heavy, vendor-specific libraries for a number that's superseded by the provider's own exact `usage` figures on every real response would add real dependency weight for a value that's only ever used pre-request (e.g. a future client-side "roughly how many tokens is this prompt" estimate) and never trusted for billing or `AIRequestLog`, which always records the vendor's own reported counts.
**How to apply**: never treat `countTokens()`'s output as authoritative — it exists for rough pre-request sizing only. If a future checkpoint needs exact pre-request counts (e.g. to enforce a hard context-window limit before sending), that's the point where a real per-vendor tokenizer dependency becomes justified.

### Cost estimation uses a static, illustrative pricing table with a fallback for unknown models
**Decision**: `cost-estimator.ts`'s `PRICING` map hardcodes a USD-per-million-token rate per model, with `DEFAULT_PRICING` covering anything not in the map.
**Why**: vendor pricing changes on its own schedule, independent of this codebase, and there's no pricing API to query live — a static table is honest about what it is (directionally useful for a future cost dashboard) rather than pretending to bill-grade accuracy. The fallback means a new model appearing in a provider's `models()` list before its pricing is added here degrades gracefully (a plausible-but-wrong estimate) rather than throwing and breaking `generate()` entirely.
**Tradeoff accepted**: `estimatedCostUsd` will drift from real vendor pricing over time with no mechanism to refresh it — acceptable since nothing in this codebase currently depends on it being exact (no billing/quota enforcement reads it).

### Gemini's streaming response is treated as newline-delimited SSE-style JSON, simplified from the real wire format
**Decision**: `GeminiProvider.stream()` parses `data: {...}` lines the same way `ClaudeProvider`/`OpenAIProvider` do, rather than implementing Gemini's actual `streamGenerateContent` response shape in full fidelity.
**Why**: the real Gemini streaming protocol has more nuance than Claude's/OpenAI's SSE conventions, and no live credentials will ever exercise this in verification (or in this phase's scope at all — `stream()` isn't called from any route yet). Treating it uniformly with the other two providers kept the three adapters symmetric and testable against the same style of mock, at the cost of not being production-accurate for real Gemini streaming.
**How to apply**: before `GEMINI_API_URL` is ever pointed at the real Google endpoint for a live streaming use case, `GeminiProvider.stream()`'s parsing needs to be revisited against Gemini's actual documented streaming response format — this simplification was a deliberate, scoped shortcut, not an oversight.

### Permanent vs. transient AI provider errors classified by HTTP status, mirroring the job system's distinction
**Decision**: each provider's `classifyHttpError()` treats `429`/`5xx` as `AIProviderTransientError` (retried by `AIService`) and everything else as `AIProviderRequestError` (not retried).
**Why**: the same shape of distinction already exists for jobs (`PermanentJobError` vs. a retryable failure) — a `429`/`5xx` usually means "try again, possibly after backing off," while a `4xx` other than `429` (bad API key, malformed request body) means "this exact request will never succeed no matter how many times it's retried." Retrying the latter would only waste `AI_MAX_RETRIES` attempts before failing anyway.
**How to apply**: any 4th provider adapter should classify errors the same way — status-code-driven, not vendor-specific — to keep `AIService`'s retry loop provider-agnostic.

### `AIService.generate()` was wired to `ContextBuilder` — but no Phase 7A `Agent` was touched
**Decision**: confirmed with the user before implementation (this phase's kickoff spec explicitly required a decision here). `AIService.generate()` now auto-builds a `KnowledgeContext` via `ContextBuilder.build()` whenever `assetId` is provided, before calling `PromptBuilder`. No `DiscoveryAgent`/`RiskAgent`/`ComplianceAgent`/`RecommendationAgent`/`ReportAgent` was modified.
**Why**: the phase's spec explicitly listed "Agent integration" under its `STOP` section (things NOT to implement), while separately requiring "PromptBuilder must now consume KnowledgeContext instead of manually assembled objects" as a hard quality requirement. Those two constraints only reconcile if the KnowledgeContext plumbing happens at the *service* layer (`AIService`, itself a Phase 7B file, not a Phase 7A `Agent`) rather than by teaching any `Agent` class to call `ContextBuilder`/`AIService` itself. This is the same reasoning Phase 7B used to justify wiring `AIService` in at all while still not modifying agents — "modify AIService" and "modify an Agent" are different scope boundaries, and only the latter was off-limits.
**How to apply**: a future Phase 7D that does integrate an agent (e.g. `ReportAgent` calling `aiService.generate({assetId, ...})` for a narrative section) needs zero changes to `AIService`/`ContextBuilder`/`PromptBuilder` to do so — the chain already auto-grounds itself end to end. That agent's own `execute()` would just need to call `aiService.generate()`, the one thing every prior phase deliberately left undone.

### Context-building failures inside `AIService.generate()` degrade gracefully rather than failing the request
**Decision**: `AIService.generate()` wraps its call to `ContextBuilder.build()` in a try/catch — on any error, `knowledgeContext` stays `undefined` and generation proceeds without it, rather than the whole `POST /ai/generate` call failing.
**Why**: `ContextBuilder`/`KnowledgeService` exist to *enrich* a prompt, not to gate whether one can be sent at all — a transient hiccup in, say, `ComplianceService.getForAsset()` (itself already calling multiple repositories) shouldn't turn an otherwise-servable AI request into a 500. This mirrors the same best-effort philosophy every event emission in this codebase already follows (`ResourceService.emitEvent` etc.) — a secondary concern's failure must never mask the primary operation's outcome.
**Tradeoff accepted**: a caller has no way to tell, from the `AIResponse` alone, whether their prompt was actually grounded in asset context or not — `AIRequestLog`/`AIResponse` don't record "context build succeeded/failed/skipped." If that distinction becomes operationally important (e.g. debugging "why did the AI not seem to know about our findings"), that's the point to add it, most likely via a field on `AIResponse` or a dedicated event distinguishing "context build failed" from "context build produced an empty result."

### Retrievers run in parallel with no dependency graph, unlike Phase 7A's agent task waves
**Decision**: `KnowledgeService.retrieveAndBuildContext()` runs every resolved retriever via a single `Promise.all()` — there is no `TaskService`-style wave partitioning, no `dependsOn`, no per-retriever retry/timeout.
**Why**: every retriever reads independently from a different (or the same, but non-conflicting) existing service — `ResourceRetriever` doesn't need `RiskRetriever`'s output the way `RecommendationAgent` genuinely depended on `RiskAgent`'s wave completing first in Phase 7A. Introducing dependency-graph machinery for six independent reads would be complexity with no corresponding requirement; the spec's own `KNOWLEDGE SERVICE` responsibilities list is "resolve, execute, merge, dedupe, sort, return" — no mention of sequencing.
**How to apply**: if a future 7th retriever genuinely needs another retriever's output first (unlikely, but possible — e.g. a hypothetical retriever that only runs if `RiskRetriever` found a score above some threshold), that's the point to reintroduce something like Phase 7A's `AgentPlanHint.dependsOn`/wave partitioning here too, rather than inventing an ad hoc special case.

### Relevance scoring reuses existing config (`config.risk.weights`) instead of inventing a parallel scale
**Decision**: `FindingRetriever` and `RecommendationRetriever` both use `config.risk.weights[severity]` directly as their `relevance` score (0-100), rather than defining their own severity-to-relevance mapping.
**Why**: `RiskService` already scores findings by configurable severity weight (`RISK_WEIGHT_CRITICAL`/`HIGH`/`MEDIUM`/`LOW`/`INFORMATIONAL`), and `Recommendation.priority` is literally typed as `FindingSeverity` (see the Phase 6A decision on why no separate `RecommendationPriority` enum exists). Reusing this one config as the relevance scale means an operator who tunes `RISK_WEIGHT_*` to change how risk scores are computed automatically gets the same tuning applied to how findings/recommendations are prioritized in AI context — one source of truth, not two scales that could silently drift apart.
**Tradeoff accepted**: `PolicyRetriever`/`RiskRetriever`/`ResourceRetriever`/`GraphRetriever` don't have an equally natural existing config to reuse (compliance outcomes don't carry severity; an asset's overall risk and its resources'/relationships' recency are different kinds of signal entirely), so those four use fixed constants or a bespoke recency-decay formula instead — deliberately not forcing every retriever into the same scoring shape just for consistency's sake.

### "Repeated entity" collapsing groups by `groupKey`, separate from `entityKey`'s exact-duplicate role
**Decision**: `RetrievedItem` has two identity-like fields — `entityKey` (exact-duplicate removal, first-occurrence-wins) and an optional `groupKey` (collapsing category for the "summarize repeated entities" requirement) — rather than overloading one field for both purposes.
**Why**: these are genuinely different operations with different granularity. Two `Finding` rows for the *same* `(resourceId, ruleCode)` would already be prevented by `Finding`'s own DB uniqueness (Phase 6A) — `entityKey` dedup here is about a retriever/merge-layer bug producing the same item twice, not a meaningful business scenario. "50 resources of the same `resourceType`" or "6 findings with the same `ruleCode` across different resources," on the other hand, are real, expected volume that would otherwise dominate a token budget — that's what `groupKey` collapsing targets. Conflating the two into one field would mean either dedup falsely collapsing distinct entities that happen to share a category, or collapsing never firing because every entity's identity is already unique.
**How to apply**: a retriever that has no realistic "many of the same category" scenario (today: `RecommendationRetriever`, `RiskRetriever`) simply omits `groupKey` — collapsing is opt-in per item, not a mandatory field.

### `PromptBuilder` takes `KnowledgeContext` as a type-only dependency, never calls into the knowledge domain
**Decision**: `prompt-builder.ts` imports `KnowledgeContext`/`RetrievedItem` as `import type` only — `PromptBuilder` has no runtime import of `ContextBuilder`, `KnowledgeService`, or `retrieverRegistry`, and never builds a `KnowledgeContext` itself.
**Why**: preserves the Phase 7B design intent verbatim — `PromptBuilder` stays "a pure function of its inputs," usable by any caller that already has a `KnowledgeContext` from wherever, without `PromptBuilder` itself knowing how one gets built (synchronously via `AIService`, via the standalone `POST /knowledge/context` route, or, in a future phase, by an agent). The coupling direction is one-way: `AIService`/routes call into `services/knowledge`; `services/knowledge`'s DTOs flow into `PromptBuilder`, never the reverse.
**How to apply**: any future addition to `KnowledgeContext`'s shape only requires updating `renderKnowledgeContext()`'s rendering logic in `prompt-builder.ts` — never a new coupling to `ContextBuilder`/`KnowledgeService` themselves.

### Bug found during this phase: `verify-ai.ts`'s `PromptBuilder` unit test still passed the removed `contextBlocks` field
**Decision**: updated the test to exercise the no-`knowledgeContext` case (asserting the user prompt passes through unchanged) instead of asserting on now-nonexistent `contextBlocks` rendering.
**Why**: `tsconfig.json`'s `include` is `src/**/*.ts` only — `scripts/**/*.ts` is covered by `pnpm lint` (ESLint) but never by `pnpm build` (`tsc`)'s type-checking, and `tsx` strips TypeScript types at runtime without re-validating them. So removing `PromptBuilderInput.contextBlocks` in `src/services/ai/prompt-builder.ts` didn't surface as a build error in `verify-ai.ts`, which still constructed an object literal with that now-nonexistent field — it silently became an inert extra property at runtime (TypeScript's structural typing simply stopped knowing about it, but nothing enforced its absence), and the test's assertion on rendered `[risk]` content failed at run time instead, when `pnpm verify:ai` was actually executed.
**How to apply**: a source-file API change (removing/renaming a field, changing a function signature) is not verified safe by `pnpm build` alone if any verify script's *own* object literals reference the old shape — always re-run every verify script whose test code touches a modified interface, not just the tests for the phase making the change. This is exactly why the regression suite (`pnpm verify:*` in full) runs every phase, not only the new script.

### Phase 7D scoped AI integration to exactly one agent (`ReportAgent`), not a shared mechanism
**Decision**: only `ReportAgent` was modified to call `AIService.generate()`. `DiscoveryAgent`/`RiskAgent`/`ComplianceAgent`/`RecommendationAgent` are untouched, and nothing was added to `Agent`/`AgentContext`/`AgentOrchestrator`/`TaskService` that would make AI calling a generic capability every agent gets for free (e.g. no `agent.generateNarrative()` on the `Agent` interface).
**Why**: the phase's spec was explicit — "Implement AI support only for ReportAgent... Do NOT modify RiskAgent, ComplianceAgent, DiscoveryAgent, or RecommendationAgent" — and separately excluded "Multi-agent collaboration" from scope. Building a shared "any agent can call AI" mechanism now, with only one real consumer, would be exactly the kind of speculative abstraction the project's standing engineering guidance warns against: a second and third agent wanting AI narratives is not confirmed to happen, and when/if it does, the actual requirements (does every agent want the same 3 templates? the same 2 modes? the same failure-handling shape?) aren't knowable yet from a sample size of one.
**How to apply**: if a future phase wires AI into a second agent, resist generalizing prematurely from `ReportAgent`'s shape alone — wait until at least two real consumers exist before extracting a shared "agent AI integration" pattern, and even then keep `AgentContext.aiMode`/`plan()`'s conditional `timeoutMs` as the template, since both were already designed to be read by any agent, not just `ReportAgent` (nothing about them is `ReportAgent`-specific — `ReportAgent` is just the only one that currently looks).

### `AgentContext.aiMode` defaults to OFF and is a 4th constructor parameter, not a breaking signature change
**Decision**: `AgentContext`'s constructor gained `aiMode: AIMode = 'OFF'` as an optional 4th positional parameter (after `signal`), rather than switching to an options-object parameter or requiring every call site to pass it explicitly.
**Why**: `AgentContext` is constructed in exactly one production path (`AgentOrchestrator.execute()`) plus several direct unit-test call sites in `verify-agents.ts` (testing retries/timeouts/cancellation/shared-context in isolation, unrelated to AI at all). A default parameter means every one of those pre-existing 3-argument call sites keeps compiling and behaving identically — `aiMode` is opt-in noise for anything that isn't `ReportAgent` under `SECURITY_REPORT`. Introducing an options object would have been more extensible for a class that already had 2+ optional constructor concerns, but `AgentContext` still only has this one, so the simpler positional-default form was preferred over designing for a generalization that isn't needed yet (see the decision above).
**How to apply**: if `AgentContext` ever needs a 2nd optional per-run setting, that's the point to refactor the constructor into an options object — don't keep stacking positional defaults past two.

### Structured/AI response separation: `data.report.aiReport` is additive, never replaces `executive`/`technical`/`asset`
**Decision**: `ReportAgent.execute()` always computes the full Phase 7A structured report first, unconditionally; the AI narrative is attached as a sibling `aiReport` key only when `aiMode !== OFF`, and even then only after the structured fields are already finalized. `buildAIReport()` never has the ability to mutate or replace `executive`/`technical`/`asset`.
**Why**: the spec required both "Structured report unchanged" as an explicit verification checkbox and that AI failure must never fail the request — the only way to guarantee both simultaneously is for the structured computation to have zero dependency on whether the AI call is attempted, let alone whether it succeeds. This also directly enables the graceful-degradation requirement: since `buildAIReport()` operates on an already-complete `structured` snapshot and only ever returns (never throws), a total AI outage degrades `SECURITY_REPORT` to exactly its Phase 7A behavior plus one `aiStatus: FAILED` marker, not a broken report.
**How to apply**: any future field added to the AI report should follow the same rule — compute structured data first, treat the AI narrative purely as commentary layered on top, never as a value the structured section depends on.

### AI narrative parsed back into fields by fixed heading, not requested as structured JSON from the model
**Decision**: prompt templates instruct the model to produce prose under five fixed Markdown headings (`## Executive Summary`, etc.), and `ReportAgent`'s `parseNarrative()` splits the raw text response on those headings — rather than asking the model to return JSON and parsing that.
**Why**: `AIResponse.text` is already a plain string (Phase 7B's provider-neutral response shape has no structured-output/tool-call channel), and real LLMs are considerably more reliable at "always start a new section with this exact heading" than at "always emit syntactically valid JSON matching this exact schema" — a single malformed brace would leave `JSON.parse()` with nothing to recover, whereas a missing heading just leaves that one field absent (`parseNarrative()` treats "no headings found at all" as "the whole response is the executive summary," a deliberately soft fallback). `SUMMARY` mode only ever asks for one heading, so its output degrades to that same fallback path trivially.
**Tradeoff accepted**: this is inherently a best-effort text convention, not a schema contract — a model that ignores the heading instruction (or a future provider/prompt change that drops it) silently produces a report with fewer populated fields, not a hard error. If stronger guarantees become necessary, the place to add them is a provider-level structured-output mode, which would be a new capability on `AIProvider`/`AIResponse`, not a change to `ReportAgent`.

### Prompt templates composed by concatenation, not a shared base-template abstraction
**Decision**: `security-report.prompt.ts` (the `FULL_REPORT` template) builds its `systemPrompt`/`buildUserPrompt` by directly concatenating `executiveSummaryPrompt`'s and `riskSummaryPrompt`'s corresponding strings, plus its own additional instructions — there's no `PromptTemplate` base class, no template-inheritance mechanism, no template registry analogous to `agentRegistry`/`retrieverRegistry`.
**Why**: there are exactly 3 templates and one composition relationship between them (`security-report` reuses the other two) — introducing a registry or inheritance hierarchy for 3 known, fixed files would be complexity with no corresponding requirement, the same reasoning already applied to keeping `PromptBuilder` a plain renderer rather than a registry-driven system in Phase 7B. Plain function composition (`buildUserPrompt` calling another template's `buildUserPrompt`) is the simplest thing that avoids the one duplication that mattered (repeating the executive-summary/risk-narrative instructions verbatim inside the full-report template).
**How to apply**: if a 4th or 5th template is ever added with its own composition needs, reconsider a registry at that point — not before.

### `CopilotService` calls `AIService.generate()` directly — never `ContextBuilder`/`KnowledgeService`/`PromptBuilder`/a provider
**Decision**: `CopilotService.chat()`'s only external call for the AI portion of its work is `aiService.generate({assetId, systemPrompt, prompt: message, focus})`. It has no import of `ContextBuilder`, `KnowledgeService`, `PromptBuilder`, or any `AIProvider`.
**Why**: the spec was explicit — "Use existing ContextBuilder -> KnowledgeService -> PromptBuilder -> AIService. Do NOT duplicate retrieval logic" and "Reuse AIService completely." Since Phase 7C already made `AIService.generate()` auto-build a `KnowledgeContext` whenever `assetId` is provided, the entire `ContextBuilder -> KnowledgeService -> PromptBuilder` chain the spec asks for is already inside `AIService` — calling it a second time from `CopilotService` (e.g. building a `KnowledgeContext` directly and rendering it manually) would be exactly the duplication the spec forbids, not a way to satisfy it. This is the same reasoning `ReportAgent` (Phase 7D) already established; Phase 8 is the second data point confirming that reasoning generalizes to a genuinely different consumer (free-form chat vs. a fixed report template) without needing to change.
**How to apply**: any future AI-consuming service should default to calling `AIService.generate({assetId, ...})` alone and trusting its internal auto-grounding — only reach for `ContextBuilder`/`KnowledgeService` directly if a caller genuinely needs the `KnowledgeContext` object itself (e.g. to render it outside of an AI prompt), which neither `ReportAgent` nor `CopilotService` do.

### `CopilotService` performs its own explicit `getOwnedAsset()` check before emitting `COPILOT_CHAT_STARTED`, even though `AIService.generate()` already checks ownership internally
**Decision**: `CopilotService.chat()` calls `getOwnedAsset(input.assetId, input.requester)` itself, first, before doing anything else — despite `AIService.generate()` performing the identical check internally whenever `assetId` is passed.
**Why**: the spec listed "Verify asset ownership" as its own explicit requirement, separate from "Reuse AIService completely" — and mechanically, `CopilotService` needs *some* ownership check before its own `COPILOT_CHAT_STARTED` event emission (which itself would perform this same check via `eventService.createForAsset`), so an unauthorized caller gets a clean 403/404 rather than a same-shaped-but-later failure buried inside event emission or inside `AIService`. The extra query is one cheap, indexed lookup and mirrors exactly how `ReportAgent`'s upstream `AgentOrchestrator.execute()` already checks ownership before doing anything else, despite `AIService` re-checking it again downstream for the AI-mode path.
**Tradeoff accepted**: a successful `POST /copilot/chat` call performs the ownership check twice (once in `CopilotService.chat()`, once inside `AIService.generate()`) — a minor, deliberate redundancy in exchange for a route that fails fast and predictably on bad input, rather than relying on a downstream service's own check being reachable first.

### Frontend JWT storage: `localStorage`, not an httpOnly cookie
**Decision**: `apps/web` stores the access/refresh token pair in `localStorage` (`lib/api/client.ts`) and attaches `Authorization: Bearer <token>` to every request, rather than having the API set an httpOnly session cookie.
**Why**: the backend (Phases 1-2) was built exclusively around a stateless Bearer-token contract — every route reads `Authorization` via `app.authenticate`, nothing in `apps/api` ever sets or reads a cookie, and the spec's own "Do NOT change backend APIs" instruction rules out retrofitting cookie-based sessions to support this. `localStorage` is the standard client-side counterpart to a Bearer-token-only API.
**Tradeoff accepted**: `localStorage` is readable by any script on the page (XSS exposure) in a way an httpOnly cookie isn't. Acceptable here because the backend contract was fixed before this phase started; revisiting it would require a backend change this phase explicitly may not make. Worth reconsidering if a future phase is ever allowed to touch auth's transport.

### One shared `useApiQuery`/`QueryBoundary` pair, not per-page loading/error state
**Decision**: every page's data fetching goes through `hooks/useApiQuery.ts` (loading/error/success state machine) rendered via `components/ui/QueryBoundary.tsx` (loading/error/empty/success branches), rather than each of the 11 pages hand-rolling its own `useState`/`useEffect` triplet.
**Why**: "show loading, empty, and error states" is a requirement that applies identically to all 11 pages — this is exactly the kind of cross-cutting, used-everywhere concern that warrants one shared abstraction rather than 11 near-identical copies (unlike a one-off page-specific need, which would stay inline).
**How to apply**: any new page added later should default to `useApiQuery` + `QueryBoundary` unless it has a genuinely one-off fetch shape (e.g. `ReportView`'s on-demand "Generate Report" action, which is user-triggered rather than mount-triggered and manages its own `loading`/`error`/`report` state directly for that reason).

### Dashboard/Risk pages compute risk client-side via one call per asset, not a bulk endpoint
**Decision**: `DashboardPage` fetches the user's asset list, then calls `GET /analysis/risk/assets/:id` once per asset in parallel (`Promise.all`) to compute aggregate stats — there is no bulk "risk for all my assets" endpoint.
**Why**: `Asset.riskScore` (a plain column on `Asset`, settable via `POST`/`PATCH /assets`) is a different field entirely from the computed `RiskScore` model `RiskService` maintains — using the former would silently show a manually-set number instead of the real, discovery-derived risk. Per "reuse existing backend APIs only, do not change backend APIs," the per-asset endpoint is the only correct source for real risk, and no aggregate route exists to add it without a backend change this phase can't make.
**Tradeoff accepted**: an N+1 pattern, acceptable at the demo/dev scale this dashboard runs at (tens of assets, not thousands). If asset counts grow, the fix belongs in a future backend phase (a bulk risk-by-assetIds endpoint), not a frontend workaround.

### `apps/web` pins ESLint to 9.x, independent of `apps/api`'s ESLint 10
**Decision**: `apps/web/package.json` depends on `eslint@^9.39.5`, while `apps/api` (and the ESLint config it hand-rolls) stays on ESLint 10.
**Why**: `eslint-config-next@16.2.11` pulls in `eslint-plugin-react@7.37.5`, whose `react/display-name` (and related) rules call `context.getFilename()` — an API ESLint 10 removed — and crash outright rather than just warning. `eslint-config-next` itself also ships a native flat-config array (no `FlatCompat`/legacy shim needed, unlike older Next versions), which was adopted directly (see `eslint.config.mjs`) since routing it through `FlatCompat` anyway hits a separate circular-JSON crash in `@eslint/eslintrc`'s validator against this plugin graph.
**How to apply**: this is a pnpm workspace, so each package's ESLint version is independent by design — there's no requirement that `apps/web` and `apps/api` match. Re-attempt the ESLint 10 upgrade for `apps/web` once `eslint-config-next`/`eslint-plugin-react` publish a compatible release; don't carry this pin forward indefinitely without checking.

### Frontend TypeScript types are hand-kept mirrors, not a generated/shared client
**Decision**: `apps/web/src/lib/types.ts` is a hand-written set of interfaces mirroring `docs/API_REFERENCE.md`'s documented shapes — there's no OpenAPI spec, no generated client, and `packages/shared` (an empty placeholder workspace) is not used to share types between `apps/api` and `apps/web`.
**Why**: the backend has no schema-generation step (Zod schemas are request-validation-only, never exported as a client-consumable spec), and introducing one purely to support the frontend would be a backend change — explicitly out of scope ("Do NOT change backend APIs"). Every shape in `types.ts` was verified by hand against the real running API during this phase (registering a user, promoting to admin via direct repository access, creating a category/asset/account, and calling every consumed endpoint — see the Phase 9 CHANGELOG entry) rather than assumed from documentation alone.
**Tradeoff accepted**: `types.ts` can drift from the backend if a future phase changes a response shape without updating both `docs/API_REFERENCE.md` and this file by hand — there's no compiler-enforced link between them. Worth reconsidering (OpenAPI generation, or finally using `packages/shared`) if the two codebases' shapes drift often enough to cause real bugs.

### Asset-scoped pages (Discovery/Findings/Risk/Compliance/AI Report/AI Copilot) are tabs under `/assets/[id]`, not top-level sidebar routes
**Decision**: the `Sidebar` has exactly 3 top-level items (Dashboard, Assets, Settings); the other 6 spec'd pages are reached via `AssetTabs`, a sub-navigation bar rendered inside `AssetPageShell` for any `/assets/[id]/*` route.
**Why**: every one of those 6 pages is inherently asset-scoped in the backend too (each of `GET /resources`, `GET /analysis/findings`, `GET /analysis/risk/assets/:id`, `GET /compliance/assets/:id`, `POST /agents/execute`, `POST /copilot/chat` takes/requires an `assetId`) — there is no "all findings across every asset" or "chat without picking an asset first" concept anywhere in the API. Structuring the frontend as asset-scoped tabs mirrors that reality instead of inventing a global view the backend has no way to answer.

### Copilot answer/citations are passed through from `AIResponse` verbatim, with no response parsing
**Decision**: `CopilotChatResult.answer` is `response.text` unmodified, and `CopilotChatResult.citations` is `response.citations` unmodified (currently always `undefined`, since `ClaudeProvider` never populates that optional `AIResponse` field). Unlike `ReportAgent`'s `parseNarrative()`, `CopilotService` does no heading-based splitting or any other post-processing of the AI response.
**Why**: `ReportAgent` needed structured parsing because its spec required five distinct named sections (`AIReport`'s `executiveSummary`/`riskNarrative`/etc.) assembled from one AI call. Copilot's spec asks for a single conversational `answer` — there's no sub-structure to extract, so any parsing here would be invented complexity with nothing to parse into. This keeps `CopilotService` the thinnest AI-consuming service in the codebase, per the spec's own "Keep CopilotService thin" requirement.
**How to apply**: if a future requirement wants Copilot answers to carry sub-structure (e.g. a distinct "suggested next questions" list), that's the point to add a parser analogous to `ReportAgent`'s — not before, and not preemptively.

### Real-time broadcast is hooked into `EventService.createForAsset()`, not into each individual emitter
**Decision**: the entire Phase 10 broadcast requirement (job updates, discovery progress, agent execution progress, AI report status, copilot status, asset events) is implemented as one hook inside `EventService.createForAsset()` — publish the just-created `AssetEvent` to `realtimeBus` — rather than adding a broadcast call to `JobExecutor`, `AgentOrchestrator`, `AIService`, `ReportAgent`, `CopilotService`, `ResourceService`, `RelationshipService`, `FindingService`, `RecommendationService`, `RiskService`, `PolicyService`, or `ComplianceService` individually.
**Why**: every one of those services already calls `eventService.createForAsset()` for exactly the events Phase 10 needs to broadcast — that was true before this phase started, across Phases 4 through 8. Hooking the one shared method they all already call satisfies "keep WebSocket logic separate from business services" more completely than hooking each service individually would: those eleven-plus services are genuinely untouched (verified: `git diff` for this phase touches exactly `event.service.ts`, plus the new `services/realtime/`/`services/websocket/` files and `server.ts`'s route registration). A per-emitter approach would have required editing every one of those files to add a broadcast call, which is both more invasive and more places to miss a new event type in the future.
**How to apply**: any future event type, in any future service, is automatically real-time the moment it's created via `eventService.createForAsset()` — no Phase 10-specific work is ever needed again for a new event type. If a future need arises to broadcast something that ISN'T an `AssetEvent` (e.g. a truly global, non-asset-scoped notification), that's a different shape of problem and would need its own hook — don't stretch `realtimeBus.publishAssetEvent()` to cover it.

### `realtime-bus.ts` is a plain `EventEmitter`, not a message queue — no persistence, no replay, no cross-process fan-out
**Decision**: `RealtimeBus` is an in-memory `node:events` `EventEmitter` subclass. There's no Redis pub/sub, no persisted outbox table, no delivery guarantee — a client that's disconnected (or a browser tab that's asleep) when an event fires simply never sees it; there's no way to "catch up" on missed events by reconnecting.
**Why**: `apps/api` is one single deployable process (see `docs/development.md`) — Redis is already in this stack (used as a job-queue fast-path signal, Phase 4) but introducing it as a second, independent transport purely to future-proof a single-process real-time feature would be exactly the kind of premature abstraction this project's engineering guidance warns against. `GET /assets/:id/events` (REST, Phase 3) already exists as the durable, replayable source of truth for anything a client needs to "catch up" on — the WebSocket layer only ever needs to carry what's new *while connected*.
**Tradeoff accepted**: if `apps/api` is ever scaled horizontally (multiple processes/instances behind a load balancer), `realtimeBus` stops working across instances — an event created by a request handled on instance A never reaches a WebSocket connection parked on instance B. That's the point to introduce Redis pub/sub (or similar) as `realtimeBus`'s backing transport, keeping its public API (`publishAssetEvent`/`onAssetEvent`) the same so `EventService`/`websocket-gateway.ts` wouldn't need to change.

### WebSocket connections have no server-side session state across reconnects — clients must resubscribe
**Decision**: `connection-registry.ts` is keyed purely by an in-memory connection id generated at `register()` time; closing a connection deletes its entry (and every reverse-index entry pointing at it) entirely. A reconnecting client — even the same user, even to the same asset — starts with zero subscriptions and must resend `subscribe` for everything it wants to keep hearing about.
**Why**: the alternative (keying subscriptions by user id instead of connection id, so a reconnect "remembers" prior subscriptions) adds real state-management complexity — expiry, multi-tab conflicts (does closing one tab drop another tab's subscriptions?), and a resource leak risk if cleanup ever misses a case — for a problem the frontend already solves more simply: `RealtimeProvider` (Phase 10 frontend) keeps its own subscription set client-side and just re-sends every `subscribe` message after each reconnect. The server stays simpler by design; the client already has to track "what do I want to hear about" for its own UI purposes anyway (which components are mounted), so asking it to resend that list costs nothing extra.
**How to apply**: `verify-websocket.ts`'s disconnect/reconnect check exercises exactly this contract (close, reconnect, resubscribe, confirm new events still arrive) — any future change to connection lifecycle should keep that check passing without weakening it into "reconnect and events resume automatically," since that's not the contract this phase built.

### The access token travels as a WebSocket query parameter, verified once at connect — not re-verified per message or on token rotation
**Decision**: `authenticateSocket()` runs exactly once, when the `GET /ws` upgrade completes. If the access token used to connect later expires (or is rotated via `POST /auth/refresh` on the REST side) while the socket stays open, the WebSocket connection is never re-checked and keeps delivering events until it closes for any other reason.
**Why**: matches the actual attack surface this phase is defending — `subscribe` is authorization-checked every time (`getOwnedAsset()` per message), so a connection can never be *widened* to cover an asset it shouldn't see, no matter how stale its original auth is. Re-verifying a token on every message (or on a timer) would add meaningful complexity (a timer per connection, a disconnect-on-expiry path, frontend handling for "your live connection just got kicked mid-session") to close a narrow window: an already-open, already-authorized connection continuing to receive events it was already authorized to receive when it subscribed.
**Tradeoff accepted**: a revoked/deactivated user (if such a mechanism existed) or a just-rotated-out refresh token wouldn't immediately sever an already-open WebSocket connection. No user-deactivation feature exists in this codebase today, so this is a theoretical gap, not an exercised one — worth closing if that changes.

### Metrics/logging hook into the existing success/failure branches of `AIService` and `job-executor.ts`, not a new cross-cutting wrapper
**Decision**: `estateai_ai_*` metrics are recorded inline inside `AIService.recordAndEmitSuccess()`/`recordAndEmitFailure()`; `estateai_job_*` metrics are recorded inline inside `job-executor.ts`'s `execute()`/`handleFailure()`. No decorator, middleware, or generic "instrument this async function" wrapper was introduced.
**Why**: both of those methods already sit at the exact single chokepoint every AI call / every job execution passes through — the same reasoning Phase 10 used for `EventService.createForAsset()`. A generic instrumentation wrapper would have been a real abstraction with only two call sites, introduced speculatively rather than because two genuinely similar things needed it.
**How to apply**: a future third "thing to meter" (e.g. a new async subsystem) should look for its own existing single chokepoint first, the way `AIService`/`job-executor.ts`/`connection-registry.ts` already had one — only reach for a shared instrumentation helper if a fourth case makes the duplication actually painful.

### `/health/ready`'s new `ai` field is informational only — it never turns 200 into 503
**Decision**: `checkAIProviderConfigured()` reports whether the configured default AI provider has an API key set, but an unconfigured provider never fails readiness — only DB/Redis unreachability does.
**Why**: `config/env.ts`'s own pre-existing doc comment already establishes that AI API keys are optional at the env layer and that `AIProviderRegistry`/`AIService` fail per-request, not at startup — a deployment that never uses AI features is a completely valid, healthy deployment. Gating readiness on it would take an otherwise-fine deployment out of a load balancer's rotation over a feature it may not even use.
**How to apply**: any future readiness check for an optional subsystem (one whose absence is a valid configuration, not a misconfiguration) should follow this same "report, don't gate" pattern; only genuinely required dependencies (DB, Redis) should affect the 503.

### Docker images run `--prod`-only `node_modules` in the runtime stage, via a separate `deps-prod` build stage
**Decision**: `apps/api/Dockerfile` has two parallel install stages off the same `base` — `deps` (full install, used by `build` and `dev`) and `deps-prod` (`pnpm install --prod`, used only by `runtime`). The compiled `dist/` (already self-contained after `tsc`, including the generated Prisma client) plus `deps-prod`'s `node_modules` is everything the runtime image ships — no `prisma` CLI, no `tsx`, no `typescript`, no test-only packages.
**Why**: the alternative (one `deps` stage, reused everywhere) would ship every devDependency into the production image for no runtime benefit — slower pulls, larger attack surface, and dependency-scanning noise for tools that will never execute.
**Tradeoff accepted**: two separate `pnpm install` runs during a full build (one per stage) instead of one — a real but small build-time cost, paid once per image build, not per container start.

### `apps/web`'s Docker runtime image preserves the monorepo's `/repo/apps/web` path nesting instead of flattening into `/app`
**Decision**: `apps/web/Dockerfile`'s `runtime` stage copies `.next/standalone`'s contents to the image root and sets `WORKDIR /repo/apps/web` (matching the build-stage layout) rather than copying into a flat `/app` directory.
**Why**: discovered empirically during this phase's verification — a first attempt that flattened `standalone/apps/web/*` + `standalone/node_modules` into `/app` crashed at boot with `Cannot find module 'next'`. Next's file-tracing for a pnpm workspace reproduces the monorepo's own relative directory structure inside `.next/standalone` (a root `node_modules/.pnpm/...` plus `apps/web/node_modules/next -> ../../../node_modules/.pnpm/next@.../node_modules/next`, a *relative* symlink) — pnpm's `node_modules` are symlinks, and flattening the tree breaks every relative symlink target. Preserving the same nesting the build stage already had is what keeps them resolvable.
**How to apply**: this is specific to pnpm workspaces + Next's standalone output; an npm/yarn-classic monorepo (real files, not symlinks) wouldn't hit this. Don't "simplify" this back to a flat `/app` layout without re-verifying the image actually boots — it looks correct and fails silently until runtime.

### Neither `docker-compose.dev.yml` nor `docker-compose.prod.yml` runs `prisma migrate deploy` automatically
**Decision**: bringing up either compose stack starts Postgres/Redis/the app containers, but a fresh database has no tables until someone explicitly runs `pnpm --filter api prisma:deploy` (locally) or `docker compose exec api pnpm prisma:deploy` (in a running stack).
**Why**: verified directly during this phase — a fresh `docker-compose.prod.yml` volume starts the API successfully (health checks pass, since those only run `SELECT 1`), but the job worker pool immediately starts logging real errors (`The table "public.SyncJob" does not exist`) until migrations are applied. Running migrations automatically in the container's entrypoint is a common shortcut, but it creates a race if a deployment ever runs more than one `api` replica (two containers racing to apply the same migration on startup) — explicit, single, deliberate migration steps avoid that entirely and match how `prisma:deploy` was already a separate script before this phase.
**Tradeoff accepted**: a first-time `docker compose up` on a fresh volume is not immediately fully functional — an operator must remember the extra migration step. Documented here and in `PROJECT_PROGRESS.md`/`TODO.md` specifically so it isn't rediscovered by surprise.

### `docker-compose.prod.yml` is self-contained, not layered on top of `docker-compose.yml`/`docker-compose.dev.yml`
**Decision**: the production compose file duplicates its own `postgres`/`redis` service definitions rather than using Compose's multi-file `-f a.yml -f b.yml` merge, `include:`, or `extends:`.
**Why**: the production and dev/infra files intentionally differ in exactly the fields that matter most for safety — production requires `POSTGRES_PASSWORD` (`:?` interpolation, fails loudly if unset) instead of the dev files' hardcoded `estateai`/`estateai`, uses named volumes with a `_prod_` suffix (so a `docker compose -f docker-compose.prod.yml down -v` can never accidentally drop a dev volume, or vice versa — this was verified directly during this phase after an unrelated ad hoc `down -v` on the prod file left the pre-existing dev Postgres volume untouched), and adds a network/nginx layer the dev files have no use for. Merging via Compose's override mechanism would make these deliberate differences implicit and easy to accidentally reconcile away in a future edit.
**How to apply**: if the three compose files ever grow enough shared boilerplate to be worth deduplicating, prefer Compose's YAML anchors within a single file family over cross-file `extends`, so the production file's safety-relevant differences stay textually obvious in one place.

### `GET /health/ready`'s new worker/queue/memory/disk checks (Phase 12) extend the "report, don't gate" pattern from Phase 11's AI check
**Decision**: only Postgres and Redis reachability affect `/health/ready`'s 200/503 status. Worker pool state, queue backlog age, process memory, and disk free space are all reported as additional fields but never flip the status to `not_ready`.
**Why**: none of these conditions mean the HTTP API itself can't serve a request — a degraded worker pool means jobs pile up, not that `GET /assets` fails; low disk/memory are early warnings, not (yet) failures. Gating readiness on them would pull an otherwise-healthy HTTP-serving instance out of a load balancer's rotation over a problem that a human, not a restart, needs to look at.
**How to apply**: any future readiness check should default to this pattern — report, don't gate — unless the condition genuinely means the process can't correctly answer requests (the same bar DB/Redis already clear). See the equivalent Phase 11 decision for the `ai` field, which this directly extends.

### Correlation IDs are scoped per unit of work (HTTP request / job / AI call), not threaded as one id across all three
**Decision**: an HTTP request's `correlationId` is its own request id (or a client-supplied `x-correlation-id` header); a job's `correlationId` in its own logs is its `job.id`; an AI call has no correlation id threaded in from whatever HTTP request triggered it. There is no single id that traces "this HTTP request → the job it enqueued → the AI call that job made" end-to-end.
**Why**: threading one id across all three would mean adding a new field to `SyncJob.payload` (written at enqueue, read at dispatch) and to `AIService.GenerateInput` (passed through `AgentContext`/`CopilotService`/every route that eventually calls `aiService.generate()`) — real, non-trivial plumbing through several files for every future caller to remember to pass along. Given the spec's "Do NOT change existing API contracts" constraint and this phase's broader scope, each unit of work getting its own independently-useful correlation id (still enough to find "every log line for this one job" or "every log line for this one request") was judged the better cost/benefit than a deeper cross-cutting change attempted under time pressure.
**Tradeoff accepted**: an operator debugging "why did the job my request enqueued fail" can't currently pivot from the request's log lines straight to the job's via a shared id — they'd go via the response body's `jobId` instead (already returned by `POST /accounts/:id/sync`/`/discover`, per `API_REFERENCE.md`). Worth revisiting as a dedicated, explicit change (not a follow-on to this phase) if true end-to-end tracing becomes a real operational need — see TODO.md.

### Discovery duration is its own metric, not just `job_execution_duration_seconds{type="DISCOVERY"}`
**Decision**: `estateai_discovery_duration_seconds` is measured directly inside `DiscoveryService.discover()`, timing only its own core work (provider call → persist → graph → analysis → policy), separately from the job-framework wrapper's own `job_execution_duration_seconds` (which additionally includes heartbeat setup and dispatcher overhead for the same run).
**Why**: the spec listed "Discovery duration" as its own tracked item, distinct from the job-queue metrics — and the two numbers do measure genuinely different things (framework overhead vs. discovery's own cost), useful to distinguish when diagnosing a slow discovery run vs. a slow job-claim/heartbeat cycle.
**How to apply**: `discover()` is called directly (not job-queued) by nothing today — every real invocation goes through the `DISCOVERY` job type — so in practice the two series will almost always move together; that's expected, not a bug, until/unless a non-job-queued caller of `discover()` is ever added.

### nginx-level rate limiting (Phase 12) is a coarser, defense-in-depth complement to `@fastify/rate-limit`, not a replacement
**Decision**: `nginx/nginx.conf`'s `limit_req_zone` (20r/s, `burst=40 nodelay`) applies to every request reaching nginx — API and frontend alike — while `@fastify/rate-limit` (`RATE_LIMIT_MAX`/`RATE_LIMIT_WINDOW_MS`) remains the app-level limit scoped to `apps/api` specifically.
**Why**: the two operate at different layers for different reasons — nginx's is meant to blunt an abusive burst before it ever reaches a container (cheap, no app logic invoked), while the app-level limit is the more precise, per-route-aware one Prometheus/logs can actually attribute to specific API traffic. Neither alone covers what the other does: nginx doesn't distinguish `/metrics` scrapes from real API calls without an explicit exemption (not added at the edge layer, unlike the app-level `allowList`), and the app-level limit does nothing for static frontend asset requests that never reach `apps/api` at all.
**Tradeoff accepted**: the two limits aren't unified into one config source — tuning one doesn't automatically tune the other. Acceptable since they're intentionally sized differently (nginx's is a rough burst-absorption ceiling, the app's is the real per-deployment traffic budget).

### Phase 13 kept Next.js 16, not downgraded to the spec's stated "Next.js 15"
**Decision**: `apps/web` stays on Next.js 16.2.11 (already in place since Phase 9) rather than downgrading to match Phase 13's spec text verbatim.
**Why**: Phase 9 already adopted 16 deliberately (App Router + Turbopack, React 19) and the app has run on it cleanly through Phases 9–13 with no compatibility issue ever surfacing. Downgrading a working, already-verified major version purely to match a spec's literal version number would be pure churn with real regression risk (React 19 + Next 16 features already used, e.g. the async `params` prop convention in every `[id]/page.tsx`) and no benefit — the spec's intent ("modern Next.js App Router stack") is already satisfied.
**How to apply**: treat spec-stated dependency versions as a floor/intent signal, not a literal pin, when the codebase already sits on a newer, working, compatible version.

### Most "top-level" list pages are asset-scoped landing pages (pick-an-asset, then reuse the existing Asset Details tab), not true cross-asset views
**Decision**: `/discovery`, `/findings`, `/recommendations`, `/compliance`, `/reports`, `/accounts`, `/resources`, `/activity` are thin pages built on one shared `AssetScopedLanding` component — pick an asset, then either navigate into that asset's existing tab route or (for Knowledge Base/Copilot) render the same content inline with an asset picker at the top. `/policies` is the one exception (a true global list, no picker), and `/risk` adds an admin-only platform-wide OVERALL score above its own picker.
**Why**: this mirrors the exact same constraint Phase 9 already documented — `GET /jobs`, `/resources`, `/analysis/findings`, `/analysis/recommendations`, `/knowledge/context`, `/copilot/chat` all require an `assetId` for non-admin callers (see API_REFERENCE.md), and there is no bulk cross-asset endpoint for any of them. Building genuine cross-asset aggregate views for all of these would require new backend endpoints — explicitly out of scope ("Do NOT modify backend APIs unless absolutely necessary"). Reusing the existing Asset Details tab routes as the actual destination also means zero duplicated view logic: `ResourcesView`/`FindingsView`/etc. are written once.
**Tradeoff accepted**: these top-level sidebar entries are pickers, not dashboards — a user has to choose an asset before seeing any data, even though the sidebar item's icon/label suggests a cross-asset overview. Called out explicitly in the session summary's "missing/deferred" list.

### Asset Details tabs expanded to 12 (Overview, Accounts, Resources, Relationships, Discovery, Findings, Recommendations, Risk, Compliance, Events, AI Reports, AI Copilot) by extracting embedded sections into their own routes
**Decision**: `AccountsSection`/`EventsSection`, previously embedded directly in `AssetOverview.tsx` (Phase 9), were extracted into their own `accounts/AccountsView.tsx` and `events/EventsView.tsx` files and given their own tab/route; `AssetOverview` itself was trimmed to an info card plus a set of quick links into every other tab.
**Why**: the spec's own Asset Details tab list names Accounts, Resources, Relationships, Recommendations, and Events as distinct tabs, not sections embedded in Overview. Extracting (not copy-pasting) the already-working Accounts/Events logic keeps this a one-time relocation rather than a duplicated reimplementation — the "no duplicated UI" requirement applies here directly.
**How to apply**: `AssetOverview` should stay a summary/index page going forward — new asset-scoped functionality belongs in its own tab, not folded back into Overview.

### The Relationships tab is a manual one-resource-at-a-time explorer, not a graph visualization
**Decision**: `relationships/RelationshipsView.tsx` lets the user pick one resource from a dropdown and lists its direct neighbors (`GET /resources/:id/neighbors`) — there's no node-link graph rendering, no multi-hop traversal UI.
**Why**: the backend's graph endpoints (`neighbors`/`children`/`parents`/`connected`/`path`) are all per-resource, one-hop-or-bounded-BFS calls, not a "give me this asset's whole graph" endpoint — rendering a real graph visualization would mean either N+1-ing every resource's neighbors (expensive, and still just a flat edge list to lay out client-side) or requesting a backend change, both out of this phase's reasonable scope given the time available.
**How to apply**: a real graph visualization (e.g. a force-directed layout) is a legitimate future enhancement, but should probably come with a backend "give me this asset's full edge list" endpoint rather than being built by brute-forcing the existing per-resource endpoints from the client.

### AI Copilot's "streaming" is a client-side typewriter reveal over the complete response, not real token streaming
**Decision**: `ChatPanel`'s `useTypewriter` hook reveals an already-fully-received assistant message progressively (a `setInterval` slicing the string), rather than rendering tokens as they arrive from the server.
**Why**: `CopilotService` (Phase 8) always calls `AIService.generate()`, never `stream()` — there is no streaming HTTP endpoint for the copilot, and adding one would be a genuine backend API change explicitly out of scope for a frontend-only phase ("Use only existing REST APIs and WebSocket events"). The spec's "Streaming responses" requirement is satisfied visually, not literally.
**Tradeoff accepted**: the full response (and its real latency) is already known before the reveal animation starts — a slow AI call is still slow, the typewriter effect just changes how the wait *feels*, it doesn't reduce time-to-first-visible-content the way real streaming would. Worth revisiting if `POST /copilot/chat/stream` (backed by `CopilotService` calling the already-implemented `provider.stream()`) is ever added — a real backend change, not something this phase could do.

### AI Copilot conversation history is entirely client-side (localStorage, per asset), never sent back to the API as prior turns
**Decision**: `lib/copilot/useConversations.ts` persists conversation transcripts to `localStorage` keyed by asset id, purely for display continuity across visits. Every `POST /copilot/chat` call still sends only the current message — no prior conversation turns are concatenated into the request.
**Why**: `CopilotService` is deliberately stateless (Phase 8, reaffirmed in ARCHITECTURE.md: "no conversation/session model of any kind") — there is no server-side conversation concept to hang a "real" history feature off of. Silently prepending prior turns to the `message` field sent to the API would change what the backend actually receives without the backend's own grounding/prompt design accounting for it, and risks quietly growing prompts past `KNOWLEDGE_MAX_CONTEXT_TOKENS`'s budget. Client-only history satisfies the spec's "Conversation history"/"Conversation list" UI requirements honestly, without pretending the AI itself remembers anything.
**How to apply**: real multi-turn AI memory would need a backend design decision (a conversation/session model, and deciding whether prior turns count toward the token budget) — that's backend scope, flagged in TODO.md, not something to fake from the frontend.

### Dashboard aggregate cards (Connected Accounts, Open Findings, Compliance Score, Recent Events) sample only the 10 most-recently-updated assets, not the full asset list
**Decision**: `loadDashboard()` fetches the full asset list (up to 50, matching Phase 9's existing risk-score N+1 precedent) for the "Total Assets"/"Recent Assets"/Risk Distribution cards, but only issues the additional accounts/compliance/events calls for the 10 most-recently-updated assets, and labels those cards "(sample)".
**Why**: there is no bulk cross-asset endpoint for accounts, findings, or compliance (same constraint as the top-level list pages above) — computing exact totals across every asset would mean 3+ extra HTTP calls per asset, which at 50 assets is 150+ requests on every dashboard load. Sampling the 10 most-recently-updated (the ones a user most likely cares about right now) keeps the page responsive while still being useful, and the "(sample)" label is honest about the limitation rather than presenting a partial number as if it were a platform-wide total.
**Tradeoff accepted**: the accounts/findings/compliance numbers can undercount a user with more than 10 assets. Acceptable at the demo/small-fleet scale this app targets today; a real fix belongs in the backend (bulk aggregate endpoints), not a frontend workaround, if asset counts grow.

### No Compliance Trend / Discovery Trend charts — no fabricated data
**Decision**: the spec's Dashboard section asks for "Compliance Trend" and "Discovery Trend" charts; neither was built.
**Why**: `ComplianceReport` is computed at query time from current data with no persisted history (`ARCHITECTURE.md`: "there is no compliance history/trend over time, only 'right now'"), and there is no discovery-run time-series list endpoint either. Rendering a trend chart would require either a backend change (explicitly minimized this phase) or inventing fake data points — the latter is actively misleading in a security dashboard and was rejected outright rather than shipped as a placeholder.
**How to apply**: if trend charts are wanted, the correct fix is a backend feature (persisted compliance snapshots on a schedule, or a discovery-run duration list endpoint) — see TODO.md. Don't retrofit fake data into these two chart slots later without that backing data existing.

### Phase 14 — `apps/api`'s Docker runtime image gained a real production `dependencies` change (`prisma`, `tsx` moved out of `devDependencies`), discovered via an actual `docker compose exec api pnpm prisma:deploy`/`pnpm prisma:seed` run, not assumed
**Decision**: `prisma` and `tsx` moved from `devDependencies` to `dependencies` in `apps/api/package.json`; the runtime stage of `apps/api/Dockerfile` now also `COPY`s the root `package.json` (for its `packageManager` field) and uses `--chown=node:node` on every `node_modules`/`dist`/`prisma` copy.
**Why**: `docs/DEPLOYMENT.md` (Phase 12) already documented running `docker compose exec api pnpm prisma:deploy` for migrations, but nobody had actually run that exact command against a real built image before Phase 14's smoke test — a `--prod` install never included `prisma`'s CLI (a devDependency) at all, so the command would have failed outright the first time anyone tried it in production. Running it for real surfaced two more layered failures: (1) `pnpm` invoked without the repo's root `package.json` present had no `packageManager` field to pin against, so corepack fetched the latest pnpm, which requires Node 22 and crashed outright on this image's Node 20; (2) even after fixing both of those, `prisma migrate deploy` failed with `EACCES` writing a small cache file under `node_modules/.pnpm/@prisma+engines`, because every `COPY --from=deps-prod`/`COPY --from=build` in the runtime stage was root-owned by default while the container runs as `USER node`.
**How to apply**: this is why Phase 14's own "Verification" step (actually running `docker build` + `docker compose up` + the exact documented migrate/seed commands against a fresh image, not just re-reading `DEPLOYMENT.md`'s prose) mattered — a documented command that was never executed against the real artifact it describes is not verified. Any future addition to `apps/api/package.json` that's needed by a `docker compose exec api pnpm ...`-style operational command (not just the running server process) needs to land in `dependencies`, not `devDependencies`, or it silently won't exist in the image that command runs against.

### Seed script (`src/scripts/seed.ts`) lives under `src/` and runs from its compiled `dist/` output, not as a standalone `tsx`-executed script under `prisma/`
**Decision**: the seed script is `apps/api/src/scripts/seed.ts`, compiled by the same `tsc` build as everything else in `src/`, and both `package.json`'s `prisma:seed` script and `prisma.config.ts`'s `migrations.seed` run `node dist/scripts/seed.js` — not `tsx prisma/seed.ts`.
**Why**: the first version of this script lived at `apps/api/prisma/seed.ts` and imported the app's own repository/service modules from `../src/...`, run via `tsx` directly against TypeScript source. That works during local development, but the production Docker image's runtime stage ships `dist/` only, never `src/` (deliberately — "no source" is one of this image's stated goals) — so `docker compose exec api pnpm prisma:seed` against the real image would have failed with a module-not-found error on every one of those `../src/...` imports. Moving the script under `src/` lets it get compiled and shipped exactly like every other module the running server already depends on, with zero special-casing.
**Tradeoff accepted**: `pnpm prisma:seed` now requires `pnpm build` to have run first (previously it worked from a fresh checkout with no build step). Consistent with `pnpm start` already requiring the same build step; not a new class of inconvenience.
