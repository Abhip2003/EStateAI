No agent is modified, no business logic duplicated, no agent's output ever mutated by another — every participant call is `orchestratorAgentRegistry.get(agentId).execute(...)`, the same call every other execution engine already makes. `WorkflowEngine`/LangGraph/the LLM Planner are all untouched.

## Phase 26 — Human-in-the-Loop (HITL) & Approval Workflows
Upgrades EstateAI with approval gates, human review, and resumable execution: an `ApprovalEngine`/`ApprovalPolicy`/`ApprovalStore` audit trail, and a `HitlOrchestrator` that pauses a workflow at a `MANUAL`-decision step (`WAITING_FOR_APPROVAL`), resumes only the newly-unblocked steps once a reviewer decides (never re-invoking an agent whose step already succeeded), and supports rejection and cancellation. Reuses Phase 25's `condition`-based skip mechanism to a new end; `WorkflowEngine`/`OrchestratorService` are not replaced or modified in their own public behavior. Does not introduce LangGraph.
- Added `src/ai/approval/{approval.types.ts, approval-policy.ts, approval-store.ts, approval-engine.ts, approval-error.ts, paused-execution.store.ts, hitl-orchestrator.ts, approval.ts, index.ts}`: `ApprovalPolicy` (mutable `register()`/`decideForAgent()`/`decideForToolPermissions()` registry — no agent registers `MANUAL` by default, since no write-capable action exists yet; Recommendation Agent is `AUTO`, everything else `NEVER`), `ApprovalStore`/`ApprovalEngine` (Redis-backed audit trail, 30d TTL, `requestApproval()`/`decide()`/`get()`/`listPending()`), `PausedExecutionStore` (persists plan/context/steps/`stepId -> ApprovalRequest id` for resume), `HitlOrchestrator` (`run()`/`resume()`/`cancel()` — builds a gated `WorkflowDefinition` via the same `condition` trick Phase 25's Plan Revision uses), `approvalFoundation` composition root.
- Added `src/routes/approval.ts`: `POST /ai/approval/request` (plans+runs a goal, gating on `MANUAL` steps), `POST /ai/approval/:id/approve` / `POST /ai/approval/:id/reject` (records the decision, then automatically resumes the execution), `GET /ai/approval/:id`, `GET /ai/approval/pending`. Registered in `server.ts`; `routes/planner.ts`/`routes/orchestrator.ts` untouched.
- Modified `src/ai/planner/plan.types.ts`: `ReasoningPlan` gained an optional `approvalRequired?: boolean` field, populated only by the new HITL layer (never by `GoalPlanner` itself, to avoid an import cycle) — absent on a plan created via the unchanged `POST /ai/planner/plan`.
- Fixed during this phase's own testing, both in `hitl-orchestrator.ts`: (1) `resume()` originally re-derived each step's `ApprovalRequest` via `ApprovalStore.listPending()`, which excludes anything already decided — the moment a request was approved or rejected it fell out of the pending list and `resume()`'s lookup silently defaulted that step's gate back to `RUN`. Fixed by persisting the `stepId -> ApprovalRequest id` map once in `PausedExecutionState` at the initial `run()`, never re-derived. (2) `'BLOCKED'` was overloaded for both a real rejection and "we just injected the reviewer's edited output, don't also run the agent" — `rejectedStepIds` computed by re-scanning the gate map afterward couldn't tell them apart, mis-reporting a clean edited-output resume as `REJECTED`. Fixed by recording `rejectedStepIds` at the moment each step's true gate is read, before the edited-output path overwrites it.
- Added `scripts/{verify-approval.ts, verify-hitl.ts, verify-resume.ts, verify-audit.ts}` (73 checks total) — policy defaults/registration/tool-permission gating, AUTO self-approval and MANUAL pending, decide()'s approve/reject/comment/edit fields, double-decide/unknown-id rejection, listPending(); a MANUAL step pausing the workflow with its dependent left SKIPPED and never invoked, approve->resume and reject->resume outcomes, a live-server backward-compatibility check; two independent MANUAL steps decided across three resume rounds with an already-approved step's agent never called twice, an edited-output resume, cancel(); every ApprovalRequest audit field populated and persisted across a real approve, plus the live /ai/approval/* routes' 404/400 handling.
- No existing agent's public contract, route shape, or workflow definition changed. `pnpm build`/`pnpm lint` clean; all four new verify suites pass; full regression sweep (`verify:ai-foundation` through `verify:planning`, all 21 prior-phase scripts) re-verified passing unchanged.

- Added `scripts/{verify-planner.ts, verify-critic.ts, verify-reflection.ts, verify-retry.ts, verify-planning.ts}` (82 checks total) — plan creation/complexity/duration/confidence/revision; per-severity findings/plan-quality findings/execution scoring/confidence aggregation; reflection synthesis for a clean and a partial/revised run plus weak-recommendation/incomplete-report detection plus store round-trips; retry classification plus a real WorkflowEngine recoverable-vs-permanent run; an in-process Plan Revision proof with a genuinely-throwing fake agent (the real Discovery Agent swallows a bad GitHub credential gracefully rather than throwing) plus a live-server HTTP run of the new planner endpoints and a backward-compatibility check against `POST /ai/orchestrator/execute`.
